AI 时代，笔记为什么该用 HTML，而不是 Markdown

Markdown 赢在“不让你排版”，因为过去排版的成本由人来出。现在 AI 替人付了这份成本，HTML 的表现力等于白送。但 AI 排版太自由，所以真正需要的是一套约束：表现力交给 HTML，一致性交给约束。

两个让我坐不住的瞬间

第一个瞬间：我用 AI 整理笔记，往里面插了一堆录音。Markdown 里的音频只能是一行链接，或者一个光秃秃的播放器，摘要、逐字稿、说话人各放各的。插到第五段，整份笔记已经乱到没法读。

第二个瞬间：参加一个黑客松，好几支队伍没用 PPT，直接打开一个 HTML 页面做汇报。页面是 AI 现场生成的，有图表、有折叠、有动效，比幻灯片好看，也比幻灯片好改。

这两件事让我想通了一个问题：Markdown 统治笔记和文档这么多年，到底赢在哪里？这个理由在 AI 时代还成立吗？

Markdown 赢在“不让你排版”

HTML 的排版能力全面强于 Markdown：多栏、卡片、对比布局、图文混排、折叠、音视频、内嵌图表。这一点没有争议。

但过去十几年，写东西的人还是选了 Markdown。原因很简单：排版的成本是人出的。手写 HTML 太累，于是我们接受了一种“只管写字、样式交给工具”的格式。

过去：人来写

排版成本由人承担，Markdown 用“放弃表现力”换来“低成本”，所以它赢了。

现在：AI 来写

对 AI 来说，写 HTML 和写 Markdown 成本几乎一样，HTML 的表现力变成了白送的。

但 AI 排版太自由，结果是另一种乱

真这么做过的人会发现一个新问题：AI 每次排的都不一样。这一份用卡片，下一份用表格；这一份紫色渐变，下一份深蓝描边；同样是“风险提示”，十份文档有十种样子。

单看每一份都还行，放进同一个资料库里，比 Markdown 还乱。我那份插满录音的笔记也是这个问题：不是 HTML 不够强，而是缺少约束。

解法：给 AI 一套受约束的排版系统

8 个

语义组件，AI 只判断内容“是什么”

1 份

主题决定长相，换主题不动正文

0 token

换肤不经过模型，一条命令完成

组件只声明语义，比如 data-hr-component="callout-warning"，长相全部由主题决定。除了视觉主题，还可以给 AI 一份文风规约和禁用词表，写完用一条命令检查。

结果是：同样让 AI 写十份会议纪要，十份长得一样整齐，录音、摘要、逐字稿永远在同一个位置。这份带录音的会议纪要就是一个例子。

改，而不是重写

AI 生成的文档总要改。常见做法是“这段不满意，整份重新生成”，结果是改好一处，坏掉三处。hReader 给每个块都标上稳定的 data-hr-id，修改按下面的顺序进行：

  1. 人：选中一句话，写下批注

    比如“这里换成具体例子”。批注存在文档内部，状态是待 AI 处理。

  2. Agent：读大纲，只读这一块

    不用把整篇文档塞进上下文。

  3. Agent：只替换这一块

    原子写入，自动留下快照，随时可以撤销。

  4. 阅读器：自动刷新

    人看到修改后的段落，决定接受还是继续批注。

技术细节见这份原理说明。

文件是你的

每份文档就是一个普通的 .html 文件，存在你自己的硬盘上，双击就能在浏览器里打开。它也不属于任何一家 AI 厂商：Claude Code、Cursor、Codex、DeepSeek，或者任何支持 MCP 或 Skill 的 Agent，都能读写同一份文档。

往后：不止笔记

HTML 能装下的东西远比 Markdown 多：幻灯片、报告、看板、交互式讲解，甚至在财务表格旁边嵌一个计算器。这些形态都有“AI 太自由”的问题，所以解法也一样。统一的嵌入外壳（media-card：音频 / 视频 + 图注 + 可折叠逐字稿）已经落地；接下来是更多主题、Markdown 导入和受控的交互组件。

展开：坦白说现状

hReader v1.0 刚刚开源，还很早期。组件目前 8 个，主题只有 1 套；排版约束已经在写入时检查（hr check、hr patch 回执里的 warnings），但只警告、不拒写；桌面版需要本机有 Node 22，安装包也还没签名，所以现阶段更推荐从 MCP 或 Skill 开始用。
