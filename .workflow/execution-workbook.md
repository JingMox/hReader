# hReader 三-agent 执行手册（Execution Workbook）

> 本文件是**流程的唯一权威**：谁写、谁审、谁测、什么条件下才能进下一张卡。规格在 `docs/`（01 调研 / 02 架构 / 03 agent 协议 / 04 视觉 / 05 卡片索引），流程在本文件，单卡的验收细则在 `.workflow/cards/<ID>.md`，过程证据在 `.workflow/reports/`。
> 版本 v2（2026-11-12）。v1 于 M1.0 期间被误删，本版按实战教训重写：每条规则背后都有一次真实事故。

---

## 1. 角色与硬边界

| 角色 | agent | 可写范围 | 禁止 |
| --- | --- | --- | --- |
| **协调者**（本会话） | 主会话 | 卡片、`docs/`、`state.md`、`git commit`、门禁探针 | 写业务代码 |
| **编写员** | `worker` | 卡片 `Scope` 列出的源码、依赖声明、`impl-<ID>.md` | 改测试、改根配置、改 `docs/`、commit |
| **审计员** | `reviewer`（只读工具） | 仅 `audit-<ID>.md` | 改任何代码 |
| **测试员** | `worker`，测试模式 | `packages/*/tests/**`、测试夹具、`test-<ID>.md` | 改 `src/`、改实现来迎合测试、改根配置 |

- 一个仓库同时**只有一个写者**（编写员干活时测试员停手，反之亦然）；审计员任何时刻可并行。
- 三角通信**只能经由协调者**：每轮结束产出一句话摘要 + 报告路径，由协调者对下一轮下"信息包"。
  （实证：M1.1 返工单把 G2 的 `path:line` + G3 的复现命令一起丢给编写员，一轮关掉 10 项。）
- 写者越界（改了别人范围）→ 不自动回退，先判断内容是否正确，再在 `state.md` 记"越界"并追认或作废。

## 2. 门禁（每张卡都必须全过才提交）

| 门 | 名称 | 执行者 | 通过条件 |
| --- | --- | --- | --- |
| **G1** | 实现 | 编写员 | 卡片 Scope 内实现 + `impl-<ID>.md`（逐条契约证据）+ `pnpm verify` 的静态五项绿 |
| **G2** | 审计 | 审计员 | `audit-<ID>.md`，`G2: PASS`，P0 = 0；P1 需协调者裁定（修 or 显式接受） |
| **G3** | 测试 | 测试员 | `test-<ID>.md`，覆盖率 100% + `pnpm verify` 全绿（含 test） |
| **G4** | 提交 | 协调者 | P0 = P1 = 0；提交信息 `feat(<milestone>): …`；`state.md` 记账 |
| **G2-R / G3.1** | 返工复审 | 审计员 / 测试员 | 定向复验返工单每一项，必须给"改前/改后"实测证据 |

- **G2 与 G3 并行**：两者都从 G1 出发，测试员独立于审计员的视角（实证：M1.1 双方各自独立命中同一个隐式闭合误报，互相印证）。
- 任何门红 → 协调者写返工单（编号 + `path:line` + 复现命令 + 修复方向 + 禁止事项）→ 编写员 R(n+1) → 复审。
- **提交粒度**：一张卡一个 commit；流程文件（卡片/state/reports）单独 `chore(workflow)` 提交。

## 3. 代码标准（要审计什么）

**可读性优先于聪明**
- 单一职责；模块头 ≤ 3 行（只写"这层管什么"）；函数 ≤ 40 行；复杂度 ≤ 10；文件 ≤ 400 行。
- 注释**只解释函数签名表达不了的东西**：量级包络、精度承诺、抛错条件、平台坑。**禁止自我认证注释**（注释声称某保证，代码不成立）——M1.1 抓到 `inject.ts` "只取前 64 字符"实际拼全文，判 P2。
- 命名表达意图，不用缩写；同一概念全仓一个词。

**接口形态**
- 公开 API 一律**裸类型**：`string` 进 `string` 出、纯数据出；不引入包装类、`Result` 对象、品牌类型。
- 失败分两类：**不可恢复**（类型系统外、文档不可解析）抛 `HrError(code)`；**可恢复**（HTML 能修）一律进 `diagnostics`，不抛、不静默丢。
- 诊断/错误码是**窄联合常量**，禁止自由字符串（M1.0 P0：`HrError` 无签名）。
- 禁止 `any` / `as` / `!` / 隐式 any；导出面最小（knip 会把"导出但没人用"判红）。

**模块分工**
- 一层一个关注点：`html/`（解析/序列化/注入）、`model/`（语义校验）、`patch/`、`compiler/`；**不得出现第二棵 HTML 树**。
- 跨包只走源码期解析 + 公开入口，不得 `import` 内部路径。

## 4. CI 纪律（最严一档）

`pnpm verify` = `format:check` → `lint`（zero-warning + 类型感知 + `no-floating-promises` 等）→ `typecheck`（`exactOptionalPropertyTypes`、`noUncheckedIndexedAccess`、`verbatimModuleSyntax`）→ `test`（`node --test` + v8 coverage，100% statements）→ `depcruise` → `knip`。

- **每完成一个功能，跑一遍完整 CI**；"静态五项绿、只有覆盖率红"可以进 G2/G3，但**不许进 G4**。
- 门禁本身要能被证伪：M1.0 P0 教训 —— `tsconfig.global.json` 未 `include` 包、跨包类型不解析、depcruise 正则零匹配、覆盖率 `skipFull`。现已固化为常驻探针：
  - **类型门探针**：临时注入错误必须让 `typecheck` 红（`pnpm gate:probe type`）。
  - **依赖门探针**：临时加一条 `renderer → core/src/html` 深导入必须让 `depcruise` 红。
  - **覆盖率探针**：删掉一条断言 / 注掉一个分支必须让 `test` 红。
  - 探针不得留在仓库里（`gate:probe` 自己负责还原）。
- 任何"改门禁让它变绿"（放宽阈值、`skipFull`、`ignore`、`exclude` 扩大）**一律驳回**；唯一例外是协调者书面裁定 + 报告留证。

### 4.1 门禁分两层跑（M2.3 血泪）：别让人靠"我只测了我改的文件"过门

| 层 | 命令 | 耗时 | 谁跑、何时 |
|---|---|---|---|
| **轻量四联** | `pnpm format:check && pnpm lint && pnpm typecheck` | ≈6s | **每个角色每次交付前必跑**，全仓范围（不是只查自己改的文件） |
| **重量四联** | `pnpm build && pnpm test:coverage && pnpm depcruise && pnpm knip` | 3–4min | 只在收口时由协调者跑一次 |

- 教训：M2.3 收尾，测试员与编写员各自只跑"定向 vitest + 自己文件的 eslint"，结果全仓 `lint` 里两条 `no-unnecessary-condition`（旧契约残影 `span?.start`）躲到最后一刻才炸。**定向检查不能替代全仓静态检查**，而全仓静态检查只要 6 秒——没有任何理由不跑。
- 报告里"轻量四联 EXIT=0"必须是**贴出来的真实输出**，不是描述。

## 5. 测试纪律

**测试不能只跑测试函数。** 每个功能至少覆盖下列六个角度，`test-<ID>.md` 逐条登记：

1. **契约正例**：卡片每一条 AC 一个可失败用例。
2. **对抗/畸形**：空、超长、超深（10k 嵌套）、Unicode 代理对、大小写混写、重复属性、未闭合、错嵌套、`</script>` 注入、`__proto__`、路径穿越。
3. **确定性/幂等**：同输入两次、换 `cwd`、换 `TZ`、并行 20 次 → 逐字节一致。
4. **不变量**：往返深等、ID 唯一、库不做不该做的写操作（`compile` 不写盘）。
5. **性能包络**：给**实测数字**（1MB / 10k 节点 / 4000 深嵌套），不写"很快"；顺带检查 O(n²)。
6. **故障注入 / 变异**：改坏实现的一个关键行，必须有测试变红（M1.0 用它抓到 11 例存活变异）。

- 测试自身也要被审计：断言必须能红（"实现坏掉会怎么红"写进报告）；`it.fails` 只能标注已知缺陷并**登记待翻牌**，修好后必须翻成 `it`。
- 覆盖率 100% 不等于测得好：不得用"只求执行到"的断言凑行覆盖。

**子进程卫生（M1.8 实测：一次 5 分钟静默挂死，整个 G3 会话被看门狗杀掉）**：

- 每个 spawn 都必须 `stdio: ["ignore", "pipe", "pipe"]` + **硬超时**（`spawn({ timeout: 10_000 })` 或 `Promise.race`）；超时算**失败**，不许跳过。
- 需要喂 stdin 时用 `["pipe", …]` 并在写入后**立刻 `end()`**；读 stdin 的子进程 + 不关 stdin = 双死锁。
- **套件不许能挂住**：挂住比失败更糟（CI 只会超时，看不到哪个用例）。

## 6. 上下文治理（三个子会话都是长跑）

- 每份报告末尾写 `ACP:` 行，内容为 `acp_status` 的上下文占用（如 `52.1K / 200K (26%)`）。
- **落盘责任人**（2026-11-14 起）：`impl-*` / `test-*` 由编写员 / 测试员自己写；**`audit-*` 由协调者写**——`reviewer` 角色没有 `bash`/`write`，它把报告正文回传，协调者原样落盘（只补 `ACP:` 去留与日期，不改 findings）。
- **阈值 55%**：≤ 55% 继续在同一会话做下一张卡（保留历史，省 re-pay）；> 55% **且当前卡已 G4** → 开新会话接手（新会话首任务固定为"读执行手册 + 最新卡片 + 上一张卡的 impl/audit/test 报告"）。
- 单卡进行中超过 70% 时，不换会话，改为要求写者先把已完成部分写进报告再继续（防丢工）。
- 协调者自己也按同一阈值行事：历史归档成交接摘要（`state.md` 顶部三段即可开工）。

## 7. 每轮的报告格式（缺一不进下一门）

- `impl-<ID>.md`：契约 → 实现映射表；自测命令与真实输出；**改前/改后数字**；"我给测试员的 5 条建议"；风险与已知缺口；`ACP:`。
- `audit-<ID>.md`：P0（阻断）/ P1（提交前必修）/ P2（可延后）三级，每条 `path:line` + 证据命令 + 修复方向；`G2: PASS|FAIL`；`ACP:`。审计员无执行权限，需要实跑才有定论的条目写成分节的 **"待核验命令"**（命令行 + 期望输出 + 若不符意味着什么），由协调者或测试员执行后把输出回贴，审计员再下结论。
- `test-<ID>.md`：用例表（含"实现坏掉会怎么红"）、覆盖率、变异/故障注入结论、性能实测表、发现的实现缺陷（只登记不修）、`ACP:`。

## 8. 卡片的生命周期

`todo → ready → in-progress(G1) → audit(G2) ∥ test(G3) → rework(R1…) → G4 → committed`
- 卡片由协调者写，**契约条款改一次 = 卡片升一版**并在卡内记修订理由（M1.1 的 P1-3 修订即范例）。
- 卡片发现规格冲突（如 `docs/02` 写 6 个大组件却列 7 个）→ 停下问协调者；协调者改 `docs/`，写者不得自行改文档。

## 10. 血泪教训（每张卡都会重犯，所以一直在加）

**10.1 反工单会引入新 P1 → G2-R 必须重审，不许"信任返工"。**
M1.4 的 R1 关掉了 8/9 条，同时**新引入 2 个 P1**（`KNOWN_FIELDS` 只认 `annotations`、`truncate.ts:122` 死臂）。规则：
- 返工后**必须**跑一次 G2-R，只审"上轮 P0/P1 + 返工触及的文件"，且必须**自己跑数字**（不读编写员自证）。
- 返工动过的每一行都算新增代码，享受同等审计待遇；"这行只是删了个三元"也要跑一次。

**10.2 测试套件会把错行为锁成"正确"。**
M1.4 的 506 例全绿，其中一条用例把 `{"annotations":[]}` 当合法 meta、把 `version`/`style` 当非法——**用户每份真实文档每次调用都会多 2 条 warning，而套件是绿的**。根因：用例用的是**手工简化样本**，不是文档样本。规则：
- 每个功能**至少一条用例的输入必须从 `docs/` 原文照抄**（贴行号，如 `docs/02:100-140`），不许手写等价物。
- 测试报告必须回答一句："如果规格文档里那个样本是错的，我的套件会不会红？"（不会红 = 套件没接住规格）。
- 变异测试不仅要"改坏实现要变红"，还要"**把规格改回旧行为要变红**"（反向变异）：把 `KNOWN_FIELDS` 改回只认 `annotations`，必须有用例红。

**10.3 变异存活 = 判定的覆盖缺口，而覆盖率 100% 掩盖它。**
M2.3 补覆盖率时，`sameSlotAs`（`packages/core/src/server/annotation-basis.ts:48`）去掉 `&& slot.depth === previous.depth` 后**全套件依然全绿**——这条"同 tag 不同层不得继承身份"的判定**零覆盖**，而行覆盖率当时看着很健康。规则：
- **变异表按"判定"列举，不按"函数"列举**。一个函数被调到不等于它的每个比较都有用例。
- 每张卡至少 3 个变异，至少 1 个必须打"判定里的第二个条件"（`a && b` 的 `b`、三元的两侧、`??` 的两侧）。
- 报告里"变异全 KILLED"必须附变异清单；**首轮 SURVIVED 是收获，不是失误**——它精确指出了哪条判定没人管。
- 覆盖率只能告诉你"这行执行过"，永远告诉不了你"这个条件被验证过"。两者缺一不可。

**10.4 死瞄代码用 `undefined` 当"未处理"信号，就是拿运行时换穷尽性。**
M2.3 的 `reduceNote`（`packages/app/src/notes-state.ts:203-211`）用 `outcomeOf(...) !== undefined` 判断"这个 intent 被处理了吗"，尾部再 `: state` 兜一下。后果：尾部兜底臂**永远走不到**（覆盖率永远差一点），而将来新增一个 intent kind 时，它会**静默地被 `return state` 吞掉**——不报错、不生效，最难查的那类 bug。规则：
- reducer 的穷尽性用**类型**表达（`Exclude<Intent, {kind:"x"}>` + 返回非 `undefined`），不靠 `undefined` 哨兵。
- 不写 `default: return state`；如果非要兜底，兜底必须**抛错**（关上门），不能静默。

## 12. 执行纪律（协调者与三个角色都适用）

**12.1 长命令会静默杀死会话。** M1.8/M2.1 共有 **3 次**会话因“串联长命令（`eslint … ; tsc … | grep`）无输出超 5 分钟”被看门狗杀掉，其中一次丢了整轮报告。
- 一条命令只做一件事，跑完 `echo DONE`；需要串联时用 `&&` 而不是 `;`（失败即停）。
- 预估 > 60 s 的命令（全仓 `verify`、变异扫描、并压测）前面先 `echo START`，后面 `echo EXIT=$?`。

**12.2 “PASS”不等于“合格”。** M2.1 的 G2-R2 判 PASS，但它自己的数据里写着“20 并发总耗时 8 s、最慢 8 s”——功能对、体验不可接受。
- 审计员的 G2 模板固定含第 6 项：**延迟/吐吐量实测 + 与基线对比**（不只看用例绿不绿）。
- 测试员的并发用例必须**同时断言正确性与时间包络**，否则并发缺陷只能靠运气发现。

**12.3 角色边界一旦被踏破，当轮就得记下。** M1.8 测试员为让 `--allow-host` 可用改了一行 `src/tokens.ts`（改对了，但越界了）。
- 跨角色修改**必须**在报告里单独立一行“越界修改 + 原因”，下一轮由正确角色重做或不重做。
- 不改代码的一方能提供的最大帮助是**指出位置与复现**，不是自己动手。

**12.4 协调者也会犯错，错误得留档。** 已发生：两次把续接 id 填成了别的角色的会话（旧 `resumeFrom` 时代）；一次派单写了不存在的路径（`src/style/css.ts:36`）；一次让 delegate 在前台跑全量 CI 导致 watchdog 杀掉整条流水线（2026-11-14，已改为后台+轮询）。
- 角色**不应盲从**协调者给的 `path:line`：先核实现状，按意图而不是按行号改，并在报告里写明“我改的位置与你指的不同，因为…”（M1.8 编写员就这么做对了）。
- 协调者每轮必须核 `state.md` 的角色行才发单。

**12.5 性能数字必须带测量口径，否则会造出不存在的 P1。** M2.1 的 G2-R2 报“20 并发 patch 8 s”，我据此派了返工；编写员量出 531 ms，差 15 倍。追查结论：审计员跑的是 **20 个独立 `hr patch` CLI 进程**（每次冷启动 Node + 解析 + 写盘），不是 20 个 HTTP 请求。同条件重跑 7.9 s 可复现，换成 daemon + keep-alive 后 449 ms/worst 445 ms，**R9 取消**。

- 任何性能结论必须同时写清：**进程模型**（独立 CLI / 同 daemon / 冷启动）、**连接复用**、**payload 大小**、**n**、**是否并行采集**。
- 两者数字不一致时，先对齐口径再决定要不要修——**不要拿一个未对齐的数字当整改依据**。
- 反向教训也成立：真实的 O(n²) 锁排队会被"总共 0.5 s"掩盖，所以曲线要跨量级（n=1/5/10/20/40/80），不能只测一个点。M2.1 实测 `total ≈ 209 + 20.6·n ms`，属线性，无拐点。
