# hReader 三-agent 执行手册（Execution Workbook）

> 本文件是**流程的唯一权威**：谁写、谁审、谁测、什么条件下才能进下一张卡。规格在 `docs/`（01 调研 / 02 架构 / 03 agent 协议 / 04 视觉 / 05 卡片索引），流程在本文件，单卡的验收细则在 `.workflow/cards/<ID>.md`，过程证据在 `.workflow/reports/`。
> 版本 v2（2026-11-12）。v1 于 M1.0 期间被误删，本版按实战教训重写：每条规则背后都有一次真实事故。

---

## 1. 角色与硬边界

| 角色 | agent | 可写范围 | 禁止 |
| --- | --- | --- | --- |
| **协调者**（本会话） | 主会话 | 卡片、`docs/`、`state.md`、`git commit`、门禁探针 | 写业务代码 |
| **编写员** | `worker` | 卡片 `Scope` 列出的源码、依赖声明、`impl-<ID>.md` | 改测试、改根配置、改 `docs/`、commit |
| **审计员** | `reviewer`（只读工具） | 仅 `audit-<ID>.md` | 改任何代码 |
| **测试员** | `worker`，测试模式 | `packages/*/tests/**`、测试夹具、`test-<ID>.md` | 改 `src/`、改实现来迎合测试、改根配置 |

- 一个仓库同时**只有一个写者**（编写员干活时测试员停手，反之亦然）；审计员任何时刻可并行。
- 三角通信**只能经由协调者**：每轮结束产出一句话摘要 + 报告路径，由协调者对下一轮下"信息包"。
  （实证：M1.1 返工单把 G2 的 `path:line` + G3 的复现命令一起丢给编写员，一轮关掉 10 项。）
- 写者越界（改了别人范围）→ 不自动回退，先判断内容是否正确，再在 `state.md` 记"越界"并追认或作废。

## 2. 门禁（每张卡都必须全过才提交）

| 门 | 名称 | 执行者 | 通过条件 |
| --- | --- | --- | --- |
| **G1** | 实现 | 编写员 | 卡片 Scope 内实现 + `impl-<ID>.md`（逐条契约证据）+ `pnpm verify` 的静态五项绿 |
| **G2** | 审计 | 审计员 | `audit-<ID>.md`，`G2: PASS`，P0 = 0；P1 需协调者裁定（修 or 显式接受） |
| **G3** | 测试 | 测试员 | `test-<ID>.md`，覆盖率 100% + `pnpm verify` 全绿（含 test） |
| **G4** | 提交 | 协调者 | P0 = P1 = 0；提交信息 `feat(<milestone>): …`；`state.md` 记账 |
| **G2-R / G3.1** | 返工复审 | 审计员 / 测试员 | 定向复验返工单每一项，必须给"改前/改后"实测证据 |

- **G2 与 G3 并行**：两者都从 G1 出发，测试员独立于审计员的视角（实证：M1.1 双方各自独立命中同一个隐式闭合误报，互相印证）。
- 任何门红 → 协调者写返工单（编号 + `path:line` + 复现命令 + 修复方向 + 禁止事项）→ 编写员 R(n+1) → 复审。
- **提交粒度**：一张卡一个 commit；流程文件（卡片/state/reports）单独 `chore(workflow)` 提交。

## 3. 代码标准（要审计什么）

**可读性优先于聪明**
- 单一职责；模块头 ≤ 3 行（只写"这层管什么"）；函数 ≤ 40 行；复杂度 ≤ 10；文件 ≤ 400 行。
- 注释**只解释函数签名表达不了的东西**：量级包络、精度承诺、抛错条件、平台坑。**禁止自我认证注释**（注释声称某保证，代码不成立）——M1.1 抓到 `inject.ts` "只取前 64 字符"实际拼全文，判 P2。
- 命名表达意图，不用缩写；同一概念全仓一个词。

**接口形态**
- 公开 API 一律**裸类型**：`string` 进 `string` 出、纯数据出；不引入包装类、`Result` 对象、品牌类型。
- 失败分两类：**不可恢复**（类型系统外、文档不可解析）抛 `HrError(code)`；**可恢复**（HTML 能修）一律进 `diagnostics`，不抛、不静默丢。
- 诊断/错误码是**窄联合常量**，禁止自由字符串（M1.0 P0：`HrError` 无签名）。
- 禁止 `any` / `as` / `!` / 隐式 any；导出面最小（knip 会把"导出但没人用"判红）。

**模块分工**
- 一层一个关注点：`html/`（解析/序列化/注入）、`model/`（语义校验）、`patch/`、`compiler/`；**不得出现第二棵 HTML 树**。
- 跨包只走源码期解析 + 公开入口，不得 `import` 内部路径。

## 4. CI 纪律（最严一档）

`pnpm verify` = `format:check` → `lint`（zero-warning + 类型感知 + `no-floating-promises` 等）→ `typecheck`（`exactOptionalPropertyTypes`、`noUncheckedIndexedAccess`、`verbatimModuleSyntax`）→ `test`（`node --test` + v8 coverage，100% statements）→ `depcruise` → `knip`。

- **每完成一个功能，跑一遍完整 CI**；"静态五项绿、只有覆盖率红"可以进 G2/G3，但**不许进 G4**。
- 门禁本身要能被证伪：M1.0 P0 教训 —— `tsconfig.global.json` 未 `include` 包、跨包类型不解析、depcruise 正则零匹配、覆盖率 `skipFull`。现已固化为常驻探针：
  - **类型门探针**：临时注入错误必须让 `typecheck` 红（`pnpm gate:probe type`）。
  - **依赖门探针**：临时加一条 `renderer → core/src/html` 深导入必须让 `depcruise` 红。
  - **覆盖率探针**：删掉一条断言 / 注掉一个分支必须让 `test` 红。
  - 探针不得留在仓库里（`gate:probe` 自己负责还原）。
- 任何"改门禁让它变绿"（放宽阈值、`skipFull`、`ignore`、`exclude` 扩大）**一律驳回**；唯一例外是协调者书面裁定 + 报告留证。

## 5. 测试纪律

**测试不能只跑测试函数。** 每个功能至少覆盖下列六个角度，`test-<ID>.md` 逐条登记：

1. **契约正例**：卡片每一条 AC 一个可失败用例。
2. **对抗/畸形**：空、超长、超深（10k 嵌套）、Unicode 代理对、大小写混写、重复属性、未闭合、错嵌套、`</script>` 注入、`__proto__`、路径穿越。
3. **确定性/幂等**：同输入两次、换 `cwd`、换 `TZ`、并行 20 次 → 逐字节一致。
4. **不变量**：往返深等、ID 唯一、库不做不该做的写操作（`compile` 不写盘）。
5. **性能包络**：给**实测数字**（1MB / 10k 节点 / 4000 深嵌套），不写"很快"；顺带检查 O(n²)。
6. **故障注入 / 变异**：改坏实现的一个关键行，必须有测试变红（M1.0 用它抓到 11 例存活变异）。

- 测试自身也要被审计：断言必须能红（"实现坏掉会怎么红"写进报告）；`it.fails` 只能标注已知缺陷并**登记待翻牌**，修好后必须翻成 `it`。
- 覆盖率 100% 不等于测得好：不得用"只求执行到"的断言凑行覆盖。

## 6. 上下文治理（三个子会话都是长跑）

- 每份报告末尾写 `ACP:` 行，内容为 `acp_status` 的上下文占用（如 `52.1K / 200K (26%)`）。
- **阈值 55%**：≤ 55% 继续在同一会话做下一张卡（保留历史，省 re-pay）；> 55% **且当前卡已 G4** → 开新会话接手（新会话首任务固定为"读执行手册 + 最新卡片 + 上一张卡的 impl/audit/test 报告"）。
- 单卡进行中超过 70% 时，不换会话，改为要求写者先把已完成部分写进报告再继续（防丢工）。
- 协调者自己也按同一阈值行事：历史归档成交接摘要（`state.md` 顶部三段即可开工）。

## 7. 每轮的报告格式（缺一不进下一门）

- `impl-<ID>.md`：契约 → 实现映射表；自测命令与真实输出；**改前/改后数字**；"我给测试员的 5 条建议"；风险与已知缺口；`ACP:`。
- `audit-<ID>.md`：P0（阻断）/ P1（提交前必修）/ P2（可延后）三级，每条 `path:line` + 证据命令 + 修复方向；`G2: PASS|FAIL`；`ACP:`。
- `test-<ID>.md`：用例表（含"实现坏掉会怎么红"）、覆盖率、变异/故障注入结论、性能实测表、发现的实现缺陷（只登记不修）、`ACP:`。

## 8. 卡片的生命周期

`todo → ready → in-progress(G1) → audit(G2) ∥ test(G3) → rework(R1…) → G4 → committed`
- 卡片由协调者写，**契约条款改一次 = 卡片升一版**并在卡内记修订理由（M1.1 的 P1-3 修订即范例）。
- 卡片发现规格冲突（如 `docs/02` 写 6 个大组件却列 7 个）→ 停下问协调者；协调者改 `docs/`，写者不得自行改文档。
