# M4.7 让测试不靠墙钟（L-43 处置 + 偶发红自查）

立卡：2026-11-18（协调者，M4.6 结卡 `d5fa538` 后）。M4.6 的教训是"门禁要能红"；本卡补的是同一件事的另一半：**红要红得可解释**。一次偶发红在 `pnpm verify` 里出现、单文件连跑 10 次全绿——这种红**只能靠重跑到绿来消化**，等于把人训练成"重跑机器"，比假绿更毒。

## 1. 证据（协调者亲测，非转述）

```
$ pnpm verify                                   # 2026-11-18，M4.6 R2 之后
 ✗ packages/core/tests/server/sse-v4.test.ts > v4#1b · 5xx 广播成 error 事件 > should broadcast an error frame instead of silently dropping the stream
   → Test timed out in 5000ms
$ for i in $(seq 10); do vitest run packages/core/tests/server/sse-v4.test.ts; done   # 单文件
 10/10 通过
```
两条事实并列时，"代码有 bug"和"测试靠墙钟"都还没被排除——本卡的任务就是把这两者分开。

## 2. 目标

**G-1 定位 `v4#1b`（`packages/core/tests/server/sse-v4.test.ts:104-126`）的偶发超时机制**
必须给出**机制级**结论，不是"加了超时就好了"。至少区分并逐一排除：
1. 产品侧竞态：`error` 事件在客户端订阅完成前发布（`hub.addClient` 与 `openSse` 的 `waitFor(1)` 之间），或 `event-ring` 在 5xx 路径上丢失帧。
2. 负载侧：`bootOf()`（临时目录 + `startServer`）+ `chmodSync` + `httpCall` 三段在 `maxWorkers: 2` 全量并发下的真实耗时。
3. 测试写法：`sse.waitFor(3)` 等的是"第 3 帧出现"，若实际只该来 2 帧（首帧注释 + error），那这条断言在**快机器上会等满超时再红**、在慢机器上表现不同——先数清应有帧数。
处置口径：**只允许把"等固定时长"换成"等事件"**（`waitFor(n)` 内部用事件驱动 + deadline）。除非能证明"慢就是应该慢"，否则**不许调大 `timeout`**；万一最终只能放宽，必须在报告里写"放宽的是 deadline 不是断言，且已证明拿到的是异步完成信号"。

**G-2 让偶发红自己说话（harness 诊断）**
`packages/core/tests/server/harness.ts` 的 `openSse(...).waitFor(n)` 在 deadline 到达时必须抛出**可诊断**的错误：已收到几帧、每帧的 `event`/时间戳、订阅建立时刻、被等待的第 n 帧是否曾以其它 `event` 名出现。判据：人为把 `waitFor(3)` 改成 `waitFor(99)` 跑一次，错误文本能让人**不看源码**就知道差在哪。

**G-3 同类扫描：全仓"靠墙钟的测试"清单**
扫 `packages/**/tests/**` 与 `packages/**/*.test.ts`、`crates` 侧 `#[test]`：
- `await new Promise(r => setTimeout(r, …))`、`sleep(…)`、`setTimeout(…, n)` 后紧跟断言；
- vitest `{ timeout: … }` 超过默认值、或 `it(..., , { retry: n })`；
- Rust 侧 `thread::sleep`。
产出一张表（文件:行 / 用法 / 判定 `确定性` | `可接受（等的是异步完成）` | `必须改`），逐条给理由。**允许"必须改"为空**，但不允许"没扫"。

**G-4 把这条规矩变成可见的门禁（可行性由 G0 判定，见 §6）**
候选方案（择一，按 G0 结论）：① `scripts/check-test-timers.mjs` 扫出上述模式，与签入的 allowlist（JSON，带理由）比对，多余/缺失都非 0，挂进 `verify`；② 只用 eslint `no-restricted-syntax` 禁 `setTimeout` 于 `tests/**`（例外走注释豁免）。**不选**任何需要人肉记忆的方案。

## 3. 非目标

- 不改 `sse-v4` 之外的业务行为；G-1 若定位到产品竞态，修 src 可以，但必须补一条能红的回归断言（不许只修测试）。
- 不引新依赖（不许 `vitest --retry`、不许 `serial_test`）。
- 不动 `maxWorkers: 2`（那是限流，不是墙钟问题）。
- 不碰 M4.6 刚立的三道门禁。

3. **编写员** 施工；**审计员** 逐条判"判据是否真能红"（要看反例证据）；**测试员** 独立复跑 + 变异（至少含：把 `waitFor` 的 deadline 去掉、把错误事件名改错、把 harness 诊断删掉）。
4. 全量门禁：`pnpm verify` **连跑 3 次全绿**（这是本卡的专属门禁：一次绿不算数）+ `pnpm desktop:check` EXIT=0（dist 产物过新先 `rm -rf`，§11.49）。

## 6. 协调者裁定（D1–D9，2026-11-18，答复 G0 的 A-1…A-7）

依据 `.workflow/reports/spec-M4.7.md`。**裁定即施工口径，写者不得自行更改；有异议先回报，不许边做边改。**

- **D1（A-1）卡面口径错了，以实测为准**：契约帧 = `ready`(1) + `error`(2)；第 3 帧是 `chmod` 触发 watcher 的 `doc.error` / `library.changed`，**是非确定量，任何用例不得等待它，也不得断言总帧数**。卡面 §2 G-1 里“首帧注释 + error = 2 帧”那句是错的，作废。
- **D2（A-2）两个 API 并存，新代码只用新的**：保留 `waitFor(n)`（不动既有 20+ 调用点，减爆炸半径），**新增 `waitForEvent(name, timeoutMs?)`**；`v4#1b` 改用后者。`harness.ts` 头注释写明：“帧数确定时用 `waitFor(n)`；等待某个事件时用 `waitForEvent`——不要用帧数去等一个可能多帧的事件”。
- **D3（A-3）不动触发器**：`chmod 000` 保留（换产品路径超出本卡）。`impl-M4.7.md` 与卡 §3 都记一条已知耦合：“该用例的 5xx 由 fs.chmod 触发，watcher 可能额外插帧，因此断言只看 `error` 事件的**存在与内容**，不看帧数”。
- **D4（A-4）helper 计入扫描面并单列**：`harness.ts:182`/`:238` 属“必须改”且**必须在本卡内修完**（AC-19）。
- **D5（A-5）G-4 降级为审计清单，不进 `verify`**：`verify` 步骤数保持 10（AC-16/AC-17 生效），AC-20 不启用。审计表必须写升级触发条件：**“必须改”类候选点 ≥ 5 处（当前 2 处），或出现第二次由“靠墙钟”引起的偶发红**——满足任一再议升级。
- **D6（A-6）证据强度**：AC-5 单文件 20 连跑 + AC-6 全量 ×3，两个口径都贴。报告里必须写一句实话：**观测到的偶发率约为 1/5 全量跑；消除偶发不能靠跑绿，本卡靠机制论证（不再等待非确定量）+ 诊断能在下次偶发时自证**。不许写“偶发已消除”这种无法证伪的结论。
- **D7（A-7）允许强断言，但只强在正确的地方**：断言 `failed.status === 500` + **恰有 1 个 `error` 帧** + 其 `data` 含 `io_failure`。**禁止**断言总帧数，**禁止**断言 `doc.error` 出现或不出现。
- **D8 deadline 必须严格小于测试预算**：`harness.ts` 新增 `SSE_DEADLINE_MS = 3000`（恒 < vitest 默认 5000），`waitFor`/`waitForEvent` 均用它；超时错误必须是 **harness 自己抛的**（带帧清单），不得让 vitest 先报 `Test timed out`。
- **D9 新增教训入档（协调者写，写者不碰 `docs/`）**：结卡时补 `docs/03` §11.54 “把非确定量数进了期望里，就会得到一条只靠重跑消化的红”。
