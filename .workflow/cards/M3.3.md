## 0. 为什么开这张卡（事实）

### 0.1 路线图里写的东西，有一半是真的

`docs/02:245-251` 描述的 DSH 插件有三处**与真实生态不一致**。这是我立卡前派调研员做证伪得到的结论（报告 `/tmp/m33-research.md`，命令与原始输出俱在）：

| 路线图写的 | 真实情况 | 证据 |
| :--- | :--- | :--- |
| `dsh plugin add @hreader/dsh-bundle` | `--profile` 是 **requiredOption**，漏了就 usage 报错 | `@deepseek-ai/dsh@0.2.2-rc.1` 的 bin |
| 插件入口 = `cordis.patch.yml` | **两份都要**：`package.json` 的 `dsh.bundle.patch: "./cordis.patch.yml"` + 该 yaml | `@deepseek-ai/dsh-agent-preset` 内 `skills/cordis-plugin-development/references/host-plugin.md:16` |
| "Prompt Hook / Prompt Interceptor 动态织入" | **这个概念不存在**。真机制是 `ctx.systemPrompt.section({name, order, text})` + `system-prompt/assemble` waterfall | `@deepseek-ai/dsh-system-prompt` 的 `lib/types/index.d.ts`；`grep -rni "interceptor\|prompt hook"` 零命中 |
| 包名生态 | `dsh@1.0.1` 是 2016 年 JS shell（撞名）、`@deepseek/harness` 404、真实组织是 **`@deepseek-ai/*`** | `npm view` 原始输出见报告 §3 |

### 0.2 我亲核过的本仓事实（2026-11-16）

| 事实 | 位置 |
| :--- | :--- |
| `export const compileTone = (tone: StyleSpec): string` —— 语言规约的**唯一**编译器 | `packages/core/src/style/tone.ts:62` |
| `export const loadStyle = (input: LoadStyleInput, deps: StyleDeps): Promise<LoadedStyle>` | `packages/core/src/style/load.ts:113` |
| CLI 已有 `hr style --tone <id>`，输出就是 `compileTone` 的结果 | `packages/cli/src/commands/style.ts:38-42` |
| MCP 已有 prompt `use-hreader-style`，同样走 `loadStyle` + `compileTone` | `packages/mcp-server/src/prompts.ts:13,58` |
| style 的 IO 装配只有一份：`nodeStyleDeps(workspace).stylesRoot` | `packages/core/src/style/node.ts:14` |
| 仓库根在 `docs/04:206` 已规划 `packages/dsh-bundle → core` | `docs/04` |

**结论**：(a) 的**内容**半边早就在了（CLI 与 MCP 两条出口都有）；缺的只有"塞进宿主 system prompt"那一步，而那一步只能由宿主的 `ctx.systemPrompt.section()` 完成。(b) 的事件契约本仓无法单独验证（没有接收方）。(c) 与 `docs/02:255`「阅读器无 bundler、无框架」直接冲突（DSH client 要求 React + `window.__ModuleLoader__.load` + `ctx.slots.inject`）。

### 0.3 这一卡要交付的到底是什么

一个**能在真 `@deepseek-ai/cordis` 类型下编译、能在假宿主下行为正确、能在真 dsh 下被装进 profile** 的插件包。它的价值不在"多一个出口"，而在**它让 (b) 的契约第一次有了类型级证明**：`ctx.emit('hreader/patch-request', payload)` 若写错一个字，`tsc` 会红。

### 0.4 拆卡留痕

调研员建议拆成 A/B/C 三卡（A 本仓零依赖、B 需真装 dsh、C 缓到 M4）。我裁定**只立 B，且限定 host-only**：

- A 已判定"本仓已具备"（`hr style --tone` + MCP prompt），不单独立卡；它唯一缺的 UX（`<file>` 位置参数在 `--tone` 下无用却必需）登记为下一卡候选，不在本卡改。
- C 移到 M4 候选，理由写进 `docs/02`（§2 交付物 D9）。

## 1. 锚点（写死，别再来问）

- **D1** **host-only**。不做 client 面板、不引 React、不产 bundler 产物。`docs/02` 的 (c) 改为"M4 候选 + 冲突理由"。
- **D2** 目录 `packages/dsh-bundle`，包名 `@hreader/dsh-bundle`，`"private": true`（本卡不发布）。
- **D3** **入口两份都写**：`package.json` 的 `dsh.bundle.patch` → `./cordis.patch.yml`；yaml 形如
  ```yaml
  - insert:
      - id: hreader
        name: '@hreader/dsh-bundle'
        config: {}
  ```
  且 `dsh.compatibility.dshReleases` 必须写（不写会被 dsh 拦）。**包名在两处出现，必须由测试断言逐字相等**，不许手抄两遍靠人眼对齐。
- **D4** `@deepseek-ai/cordis` 与 `@deepseek-ai/dsh-system-prompt` **只作 `devDependencies`，精确版本（不用 `^`/`~`）**；源码里**只用 `import type`**。理由：dsh 从 profile 的 `node_modules` 解析插件，插件自带一份 cordis 会造成两份实例、`interface Events` 的 declaration merging 失效——**这是本卡最容易埋的静默错误**。
- **D5** 类型合并写 `declare module '@deepseek-ai/cordis'`，**不是** `'cordis'`（上游 `cordis` 是另一条发布线）。`Events` 里加 `'hreader/patch-request'`，`Context` 里若 `dsh-system-prompt` 已声明 `systemPrompt` 就不要重复声明。
- **D6** 织入用 `ctx.systemPrompt.section({ name, order, text })`。`order` 取值必须**在注释里给理由**（**真常量**取自 `@deepseek-ai/dsh-system-prompt@0.2.2-rc.1` 的 `lib/types/index.d.ts:123-152`：`HARNESS_IDENTITY: -1000` / `DEPLOYMENT_PERSONA_PREFIX: 0` / `PLAN_POLICY: 500` / `TOOL_BASH: 1000` 起是工具指引。**F1 更正**：本卡初稿写的 `-100`/`100-199` 是错的（那是更早版本的带位），立卡时未核包内真值——语言规约属 persona 级，取 `100` 落在 persona 之后、policy 之前）。`text` 必须**逐字节等于** `compileTone(loadStyle({id}, deps).spec)`——与 CLI/MCP 同一份编译器，不许在本包内二次拼接文案。
- **D7** `workspace` 从哪来**必须查证**，不许猜。候选：宿主的某个 ctx 字段 / `process.cwd()` / config 必填。查证过程（命令 + 原始输出）写进交付报告。**若查不到**：把 workspace 做成 config 必填并 fail-fast 抛可读错误，同时在 `docs/05` 写明"为什么不能自动推断"。
- **D8** 可逆卸载：所有注册走 `ctx.effect`（或 `ctx.on('dispose')`），dispose 后 section 被移除；**重复 apply 幂等**（不产生第二个 section）。
- **D9** 未知 `styleId`：二选一并钉用例——(i) fail-fast 抛可读错误（列可用 id），或 (ii) 退默认风格 + warn。**倾向 (i)**：宿主的 prompt 里混进一个"退默认"的风格，作者永远不会发现自己的 styleId 拼错了。
- **D10** **本卡不许改 `packages/core`、`packages/mcp-server`、`packages/cli` 一行**。需要的东西不存在时，停下来记 `L` 级缺陷。

## 4. 验收（每条可脚本化，不许"目测通过"）

- **AC-1 入口合规**：`package.json` 的 `dsh.bundle.patch` 指向**存在**的文件；`cordis.patch.yml` 是 `[{insert:[{id,name,config}]}]` 形状；`cordis.patch.yml` 里的 `name` 与 `package.json` 的 `name` **逐字相等**（测试断言，不是人眼）；`dsh.compatibility.dshReleases` 存在且非空。
- **AC-2 类型契约真对齐（本卡的核心）**：`tsc` 在真 `@deepseek-ai/cordis@4.1.0` 与 `@deepseek-ai/dsh-system-prompt` 的 d.ts 下编译通过；`ctx.emit('hreader/patch-request', payload)` 类型正确；**两条负例**用 `// @ts-expect-error` 钉住（少传参数 / payload 类型错）——`tsc` 会验证该指令有效，改对了反而报"未使用的 expect-error"。
- **AC-3 织入内容逐字节一致**：假宿主单测断言 `systemPrompt.section` 收到 `text` 与 `compileTone(loadStyle(...))` **逐字相等**（`toBe`，不是 `toContain`）。
- **AC-4 可逆卸载 + 幂等**：dispose 后无残留 section；连续 `apply` 两次只有一个 section（D8）。
- **AC-5 未知 styleId 的行为**（D9 二选一）钉住，且错误信息里**列出全部可用 id**。**判绿硬条件**：用例必须断言出现一个**非默认**的 id（只断言“含默认 id”等于让“只列默认 id”的实现混过去——审计员 G2-R1 已抓到这个口子）。
- **AC-6 workspace 来源**：按 D7 查证的结论落地，并有一条用例覆盖"拿不到 workspace 时"的行为（fail-fast 的可读错误 / 自动推断成功）。
- **AC-7 零外部运行时依赖**（原文“运行时零 import”是错的措辞，F1 落地后裁定改为本句）：**允许** `node:` 内建与 `@hreader/core`（单实例风险只针对 `@deepseek-ai/cordis`，core 由 `dist/index.js` 内联）；**禁止**任何 `@deepseek-ai/*` 或第三方包的**值**导入（`import type` 允许）。判据三层：① `dist/**`（含 `*.js.map`）零命中 `@hreader/core`/`workspace:*`/`from "@deepseek-ai/`；② `src/**` 对非 `node:`、非 `@hreader/core` 的包只有 `import type`；③ 两层断言都必须带**非空集合下界**（`expect(FILES).toEqual(expect.arrayContaining([...]))`），否则目录一变就恒绿。
- **AC-8 烟测**：`pnpm smoke:dsh` 在未装 dsh 时 SKIP（退出码 0 + 明确日志），装了则真跑 `add` 并断言 profile 里出现本插件。
- **AC-9 文档**：`docs/02` 三处不实已改、`docs/05` 使用节齐、`docs/04` 依赖图对上、`skills/hreader/SKILL.md` 同步。

## 5. 风险点（三方都要盯）

1. **rc 依赖会漂**：`@deepseek-ai/*` 全线 rc（`dsh@0.2.2-rc.1`、`dsh-system-prompt` latest `0.0.1-rc.1` / next `0.2.2-rc.3`）。精确版本 + 一条"若上游类型变了会在哪里红"的说明写进 `docs/05`。**不许**用 `^`/`~` 让 CI 某天自己变红。
2. **两份 cordis 实例**（D4）：任何 `import`（非 `import type`）都会造成静默失效，AC-7 就是为它设的。
3. **`Events` 合并目标写错模块名**（`'cordis'` vs `'@deepseek-ai/cordis'`）：错了不会报错，只是校验失效——所以要有负例（AC-2）。
4. **`order` 取值**：写错不会报错，只会让风格规约在 prompt 里排到不合适的位置。必须给理由。
5. **`cordis.patch.yml` 的 `config` 传什么**：若 workspace 走 config（D7），yaml 里的 `config: {}` 就得改成带字段，两处（yaml 与 `apply` 的默认值）必须同一份事实。

## 6. 测试要求

- **假宿主**：`{ provide, effect, on, systemPrompt: { section }, baseDir? }`，记录每次调用（含 dispose 回调）；`section` 记录 `{name, order, text}`。
- **变异自证（至少 5 条，每条要贴"删掉哪一行 → 哪条用例红"）**：
  1. 删 `provide` 调用；2. `order` 改成 0 或 -100；3. `text` 改成 `styleId` 字符串（"请用 X 风格"这种缩水实现）；4. 删 dispose 清理；5. `declare module` 的模块名改成 `'cordis'`（AC-2 的负例会红吗？——这条要专门试，答"不会红"就是 AC-2 用例不够）。
- **不许用 `toContain` 验证规约文本**（§11.14）。
- **两个必须显式排掉的假绿形态**（写者自证、测试员变异复验）：
  1. **空集合恒绿**：任何“grep 源码/产物后断言零命中”的用例，都必须先断言被扫文件非空、且扫描口径能命中一个**故意放进去的正例**（加 `Probe` → 必须红）。
  2. **断言与实现同源**：断言若复用了被测函数的推导路径（例如用 `resolvePatch` 自己算期望值），它只能证明“自己等于自己”。期望值必须是**独立字面量**。
- 覆盖率：`packages/dsh-bundle/src/**` 四维 100%。
