## 0. 为什么开这张卡（事实，不是判断）

M3.1 交付后有三个"上线就废"或"上线就会漂"的洞，全部来自**同一事实被拼写两次**：

1. **`L-21` 产物离开仓库即失效**。`hr_apply_style` 对三个内置预设 100% 失效：`stylesRoot` 由"模块 URL 往上 N 层"推出来，bundle 拷到仓库外就指向不存在的目录。实测（M3.1 期间）：`cp dist/main.js /tmp/installsim/` + `hr_apply_style {visualId:"atelier-editorial"}` → `[unknown_style]`。
2. **`L-13` 路径策略两份**。`packages/mcp-server/src/tools/target.ts` 逐字镜像 core 的 `isInside`/`isInsideOrSelf`，因为 core 的 `packages/core/src/io/paths.ts:35` 有 `export const isInsideOrSelf`，但 `packages/core/src/index.ts` 对它 0 命中（barrel 没导出）。审计员逐字比对确认**当前等价**——但"等价"不是"不会漂"：本轮已经漂过一次（`..foo` 判定分叉，见 `L-26` 那轮的 F5）。
3. **`L-17` 产物入口靠测试兜底**。`knip.json:41-42` 的 `packages/mcp-server.entry` 只有 `src/index.ts`，真正 `bin` 的 `src/main.ts` 只靠 `tests/cli.test.ts` 的 `await import("../src/main")` 才可达。

**判据（本卡立为硬标准）**：同一事实——"仓库根在哪、`styles/` 子树在哪、什么算界内"——**只许拼写一处**。注释挡不住漂移，只有 import 能。

## 1. 契约（AC）

## 2. 锚点推导（写死，别再来问）

`packages/mcp-server/src/styleDeps.ts` 与 `packages/mcp-server/dist/main.js` **都恰好比包根深一层**，所以

```ts
new URL("../styles/", import.meta.url)   // src/ 与 dist/ 两种布局都指向 <pkg>/styles
```

是唯一不需要分支的锚点。于是包内布局天然成立：build 把 `styles/` 拷到 `<pkg>/styles`，运行时 `../styles/` 命中；该候选缺失时（源码直跑、未 build）再退回 core 给的仓库根。**候选顺序必须"包内优先"**：发布版的包内才是真值源，仓库根只是开发期兜底。

`<pkg>/styles` 是**生成物**：加进 `.gitignore`；`packages/mcp-server/package.json` 的 `files` 将来发布时若需要，由发布卡处理（本卡不改 `private: true`）。
