## 0. 为什么开这张卡（事实）

前端与 HTTP 早就有撤销（`revertLast` + `POST /api/doc/:docId/undo`），MCP 六个工具里没有。后果不是"少个按钮"，而是**Agent 改错了只能再 patch 一次覆盖**——覆盖会丢掉"写前字节"，而撤销是把写前字节原样放回去。两条路径的语义差一辈。

## 1. 锚点（写死，别再来问）

- **D1** 只加 `hr_undo` 一个工具，输入 `{ filePath }`。**不引入 `steps`/`toSnapshot`**：多步撤销要枚举快照链，快照命名与排序语义未定义，属 P2 非目标。
- **D2** 调 `revertLast`，**不直接调 `undoPatch`**——错误码映射只有一份，走 second path 就会长出第二份。
- **D3** 返回 `RevertResult` 原样 JSON（`path/bytes/restoredFrom/sha256/revision`），不裁字段：Agent 需要 `revision` 对齐前端刷新，`restoredFrom` 是审计线索。
- **D4** 不涉及 cookie/csrf（MCP 是本地进程，不是 HTTP 面）；workspace = `process.cwd()`，与其它五个工具同一条路。
- **D5** `nothing_to_undo` 走 `guarded` 的 `isError` 工具结果，绝不抛到 SDK 层（`packages/mcp-server/src/errors.ts` 既有条款）。
- **D6** **本卡不许改 `packages/core` 一行**。`revertLast` 或 `nodePatchDeps` 的形状不够用时，停下来记一条 `L` 级缺陷，别顺手改 core。
- **D7** 工具描述与既有六个同一语气，且要写出**选路理由**（工具描述是 Agent 唯一的选路依据）：撤销是"把写前字节放回去"，再 patch 一次是"用新内容覆盖"——改错了前者才对。
- **D8** `revertLast` 的第三参 `options` 传什么必须**显式决定 + 写注释**。HTTP 侧传 `LOCK_WAIT_MS`（`write-replies.ts:44`）；MCP 侧若用默认 `{}`，锁等待语义与 HTTP 不同源，要在 `docs/05` 里说明。

## 2. 用户可见行为（可当验收脚本）

1. 建 doc → `hr_patch_node` 改一个节点 → `hr_undo` → **文件字节**回到 patch 之前，`revision` 与 undo 前不同。
2. 连调两次 `hr_undo` → 第二次 `isError` + `nothing_to_undo`（第一次已删掉唯一快照）。
3. 对**从未写过**的 doc 调 `hr_undo` → `nothing_to_undo`，不是 `internal`。
4. 对不存在的路径 → `not_found`；对目录 → `not_a_file`（与其它工具同一映射）。
5. `hr_undo` 之后 `hr_outline` → 大纲反映还原后的内容（不是缓存）。

## 3. 验收标准（AC）

- **AC-1 有效性**：§2 五条全绿，且判定用**文件字节**（不是"工具没报错"）。每条断言要能回答"我删掉实现里哪一行它会红"。
- **AC-2 错误码诚实性**：三条错误分别得到 `nothing_to_undo` / `not_found` / `not_a_file`，一条不许落 `internal`。**反向一条**：`undo_unavailable`（core 内部码）不得出现在 MCP 工具结果里。
- **AC-3 栈序**：`hr_patch_node` → `hr_apply_style` → `hr_undo` 只回退 style，再 `hr_undo` 回退 patch，第三次 `nothing_to_undo`。这钉的是**栈**语义（后进先出），不是"退回到某个版本"。
- **AC-4 并发**：两个 `hr_undo` 并发 → **恰好一个成功、一个 `nothing_to_undo`**。两个都成功意味着删掉两份快照并还原两个不同状态，必须被拦。
- **AC-5 注册表**：原有六个工具的 `inputSchema`/名字/描述不变；`hr_undo` 进 `index.test.ts` 的名字集合；`tools/index.ts` 的"六个工具"注释改成准确数字。
- **AC-6 文档**：`docs/05-feature-cards.md` 加 M3.4 小节（工具表行 + 一行使用建议 + 验证节）；`skills/hreader/SKILL.md` 若列了工具清单则补 `hr_undo`。
- **AC-7 覆盖率**：`packages/mcp-server/src/tools/undo.ts` 语句/分支/函数/行 四维 100%（`vitest.config.ts` 的 `perFile` 门槛不容许例外）。

## 4. 契约（裸类型）

```ts
export const undoShape = { filePath: z.string().min(1).describe(FILE_PATH_HINT) };
export const undoCall = (args: { filePath: string }): Promise<CallToolResult>;
```

返回值与 `patchNodeCall` 同形：`okResult(result, { ui: { resourceUri: `${UI_URI_PREFIX}${docIdOf(target.file)}` } })`——让 MCP-UI 客户端在撤销后也刷新那张阅读器卡片。

## 5. 风险点（审计重点）

- **R-1** "六个工具"这类数字散落多处（`tools/index.ts` 注释、README、`SKILL.md`），漏改就是文档说谎。
- **R-2** `options` 传不传（见 D8）：锁等待语义是否与 HTTP 同源。
- **R-3** `okResult` 的 `_meta.ui.resourceUri` 用 `docIdOf(target.file)`：undo 后 doc 仍在，URI 有效；但"doc 被删而快照还在"的路径要落到 `not_found`，不许 500。
- **R-4** 快照被外部删除（有人手工清 `.hr/undo/`）→ `restore` 里的 `unlinkOf` 失败会不会留半还原状态。写者要回答，审计员独立判。

## 8. 这张卡为什么存在（一致性反问）

价值不在"多一个工具"。价值在**让 MCP 与 HTTP 两条写入路径共享同一条快照栈**。所以审计重点该放在"两条路径是否真的同源"（同一个 `revertLast`、同一把锁、同一份错误码），而不是工具本身的接线——接线错了，一个 `grep undoPatch` 就查出来了。
