# hReader 三角色协作工作流 (Collaboration Workflow)

> [!IMPORTANT]
> 本文档是 hReader 项目的**协作契约**。它定义了协调者（主会话）与三个执行角色（编写员 / 审计员 / 测试员）的职责边界、交付物、门禁（Gate）、通信协议、返工规则与上下文生命周期。
>
> 任何角色在任何时候都不得越过本文档规定的边界。规则冲突时，以本文档 + [04-engineering-standards.md](04-engineering-standards.md) 为准；仍冲突则升级给用户裁决。

---

## 一、角色总览

| 角色 | 技术载体 | 工具权限 | 写入范围 | 一句话职责 |
| :--- | :--- | :--- | :--- | :--- |
| **协调者**（主会话，用户直连） | 主 Pi 会话 | 全部 | 仅 `docs/`、`.workflow/` | 拆卡、派活、转发消息、裁决、验收。**不写任何产品代码，不跑实现类命令** |
| **编写员** (Writer) | `subagent` 工具，`worker` 角色，独立会话 | read / edit / write / bash | `packages/**/src/**`、`packages/**/package.json`、构建与 CI 配置、`styles/**`、`skills/**` | 实现功能、写配置、修 P0/P1、写实现报告 |
| **审计员** (Auditor) | `subagent` 工具，`reviewer` 角色，独立会话，**纯只读（无 `bash` / `write`）** | read / grep / find / ls / watchdog_diff | **无写权限**：报告以正文回传，由协调者落盘到 `.workflow/reports/audit-<card>.md` | 审计代码与测试质量，输出可执行的 P0/P1/P2 清单 |
| **测试员** (Tester) | `subagent` 工具，`worker` 角色，独立会话，**测试专用边界** | read / edit / write / bash | 仅 `**/tests/**`、`**/*.test.ts`、`**/*.spec.ts`、`tests/fixtures/**`、`vitest.config.*` | 设计并实现测试、做多角度对抗验证、写测试报告 |

> **角色载体（2026-11-14 起）**：子代理由 `pi-subagents` 插件提供（`subagent` 工具），续接用 `action: "resume"`；旧的 `acp_delegate` / `resumeFrom` 写法作废。`reviewer` 角色**没有 `bash` 与 `write`**，因此：①审计员不能自己落盘报告——它把报告正文回传，协调者写进 `.workflow/reports/audit-<card>.md`；②审计员不能自己跑命令核验——它把"要跑什么、期望看到什么"写成"待核验命令"，由协调者或测试员执行并回贴输出。这是权限换来的可审计性，不是效率损失。
>
> 三个子代理角色统一 `thinking: low`（`~/.pi/agent/settings.json` 的 `subagents.agentOverrides`），主会话保持 `high`。派单时若传 `model` 参数，必须带 `:low` 后缀，否则会覆盖掉该默认。

### 1.1 协调者（主会话）—— 只做协调，不写代码

允许做的事：
- 读取代码/文档用于**判断**（review 结果、定位问题、写任务卡）。
- 拆解功能卡、写/更新 `.workflow/` 状态与报告、转发角色间的消息。
- 裁决冲突、控制返工轮次、执行最终验收（`git` 提交与打 tag 除外——见 §3.6）。
- 用只读手段验证"证据真实性"（例如抽查审计员引用的 `file:line` 是否存在）。

禁止做的事：
- 修改任何 `packages/**`、`styles/**`、`skills/**` 下的产品代码或配置。
- 代替编写员实现功能、代替测试员写测试、代替审计员下结论。
- 因为"子会话太慢"而自己动手。慢就等，或换更快的模型档位。

### 1.2 编写员 (Writer)

职责：
- 按功能卡实现。范围严格限定在卡片的 `Scope` 内，发现必须扩大范围时**停下来报告**，不得擅自扩张。
- 保持 [04-engineering-standards.md](04-engineering-standards.md) 的全部硬性要求（可读性、注释规约、裸类型 API、架构边界）。
- 自测：至少证明"功能在真实路径上跑通一次"（CLI 实跑 / 真实文件读写），再交卡。
- 开发期间只跑**单文件定向测试**（`pnpm vitest run <单个测试文件>`）与改动文件的 `eslint` / `tsc --noEmit`；**全量 `pnpm verify` 由协调者在收口时跑 1 次**（见 §3.6 与 §11.10）。
- 交卡时必须附：定向测试的真实输出 + "哪些改动没被定向测试覆盖、为什么"。
- 处理审计员与测试员提出的 P0/P1；P2 可排期但必须在卡片里登记。
- **绝不修改测试文件**。若认为测试断言有误，交由协调者转给测试员。

### 1.3 审计员 (Auditor)

职责：
- 审计代码：可读性、命名、注释是否只解释"签名表达不了的东西"、裸类型 API 是否被包装类污染、封装与模块边界、错误处理、边界条件、性能陷阱、跨平台路径、安全性（HTML 注入 / 路径穿越 / 原型污染）。
- 审计架构：职责是否单一、依赖方向是否单向、公开 API 面是否最小、是否存在隐式全局状态。
- 审计**测试本身**：同义反复断言、过度 mock、只断言不验证、快照倾倒、缺负路径、缺并发/错误路径、测试是否真的能抓到 bug（变异测试结果的可信度）。
- 输出 finding：`P0`（阻断：错误行为/安全隐患/架构破窗）、`P1`（必须本卡修复：可读性差、契约不清、测试薄弱）、`P2`（可排期）。每条必须带 `path:line`、复现/推理、要求的修复方向。
- **只读**。`reviewer` 没有 `bash`/`write`：不许改代码，也不能自己落盘。报告以**正文**回传，协调者写入 `.workflow/reports/audit-<card>.md`。
- 需要跑命令才能定的结论，写成"待核验命令"（完整命令行 + 期望输出 + 若不符则说明什么），由协调者或测试员执行并把真实输出回贴给你。
- 结论必须能落到 `path:line`；读不到的结论标 `UNVERIFIED`，不许用"通常/大概"代替证据。

### 1.4 测试员 (Tester)

职责：
- 为每张卡建立**测试计划**（先写计划再写断言），覆盖 §4 的多角度矩阵。
- 写测试代码并跑全量 CI，给出覆盖率与变异测试结果。
- 做**功能外对抗实验**：不使用测试函数，而是像用户/攻击者一样从黑盒角度尝试打坏它（真实 CLI 调用、坏输入、超大输入、编码/换行/路径边界、并发、断电式中断、重复执行幂等性）。
- 回答一个明确的问题：**"有没有办法引起这个功能的 bug？"** 必须给出结论 + 尝试过的手段清单 + 未覆盖的风险。
- 发现实现缺陷时**不修源码**，登记到报告并交协调者转编写员。
- 输出 `.workflow/reports/test-<card>.md`，包含：测试矩阵、执行的命令、实际输出摘录、覆盖率、变异分数、未覆盖风险。

## 二、工作单元：功能卡 (Feature Card)

一切工作以卡片为单位。卡片由协调者创建，存放在 `.workflow/cards/<card-id>.md`，格式：

```markdown
# CARD <id> — <标题>

- 里程碑: M1 / M2 / M3 / M4
- 依赖: <card-id 或 无>
- 状态: todo | implementing | auditing | testing | rework | accepted | blocked
- Scope(写): 允许修改的路径（白名单）
- Out of scope: 明确不做的事
- 用户可见行为: 一段话，能当作验收脚本
- 验收标准 (AC): 编号列表，可机械判定
- 契约: 公共 API 签名 / CLI 输出 / 文件格式（裸类型，见 04 文档）
- 风险点: 已知的坑与需要特别审计的地方
```

卡片拆分原则：单卡应能在**一次编写员会话内**完成；单卡新增/修改源码建议 ≤ 400 行；跨包改造必须拆卡。

## 三、门禁 (Gates) 与流程

```text
G0 拆卡(协调者)
   → G1 实现(编写员) ──────────────────────┐
   → G2 审计(审计员) ─┐（并行，只读）        │ 全量CI绿 + 自测证据
   → G3 测试(测试员) ─┘（并行，只写 tests）  │
        ↓                                   │
   G4 裁决(协调者): 无P0/P1 且 测试全绿 且 覆盖/变异达标 ?
        ├─ 否 → G4' 返工(编写员/测试员) → 复审 → G4（最多 3 轮）
        └─ 是 → G5 验收(协调者): 更新 state、打 tag、记录卡片 accepted → 下一张卡
```

### 3.1 G0 — 拆卡（协调者）

- 从 [02-architecture-and-roadmap.md](02-architecture-and-roadmap.md) 的里程碑任务拆出卡片。
- 卡片必须写清 `Scope` 与 `Out of scope`；没有 Scope 不许开工。
- 一次只推进**一张**卡（串行推进，避免多写者冲突）。允许"实现 A 卡的同时，为已交卡的 B 卡做审计/测试"，但同一时刻仓库里**只能有一个写者**。

### 3.2 G1 — 实现（编写员）

交付物（缺一不可）：
1. 变更代码 + 必要的配置。
2. 全量 `pnpm verify` 全绿输出（**收口时由协调者跑**，贴 tail 摘要含各步骤 PASS；开发期间用定向测试代替）。
3. 自测证据：真实命令 + 真实输出（不是"单元测试通过"）。
4. 变更说明：做了什么、为什么这样设计、有没有偏离卡片契约。
5. 一个 commit（见 §3.6）。

### 3.3 G2 — 审计（审计员）

- 输入：卡片 + `git show --stat`/`git diff` + 全量 CI 结果。
- 必须逐条回答卡片 `AC`：每条 AC 是否有代码/测试支撑，支撑是否真实。
- 必须给出：`P0/P1/P2` 清单（可为空，但要写"我检查了 X/Y/Z，未发现问题"的检查项清单，防止空转）。
- 必查清单（每次都要过一遍）：命名与可读性、注释是否复述代码、裸类型契约、错误路径、边界（空/超大/Unicode/CRLF/路径穿越）、并发与重入、资源释放、跨平台、公开 API 面、依赖方向、测试有效性。

### 3.4 G3 — 测试（测试员）

- 先交**测试计划**（矩阵 + 攻击面），再交测试代码。
- 硬性门槛（未达标即 G4 失败）：
  - 全量 CI 绿。
  - 行/分支/函数/语句覆盖率 ≥ **90%**（核心 `packages/core` ≥ **95%**）。
  - 关键纯逻辑（解析器、ID 生成、Patch 计算、Outline 提取）跑**变异测试**，mutation score ≥ **75%**。
  - 至少 1 个"用户视角黑盒实验"（真实 CLI/真实文件/真实浏览器）。
  - 至少 1 个负路径 × 每类错误（不存在的文件、非法 HTML、非法 selector、超长输入、权限不足）。
- 报告必须能给协调者直接判卷：命令可复制、输出可核对、结论明确。

### 3.5 G4 — 裁决（协调者）

通过条件（全部满足）：
- 审计：无 P0，无未处理的 P1。
- 测试：CI 绿 + 覆盖率/变异达标 + 无 P0/P1 缺陷。
- 卡片 `AC` 逐条有证据。
- 无越界修改（`git diff --stat` 范围与 `Scope` 一致）。

不通过 → 返工，规则见 §6。

### 3.6 G5 — 验收与提交

- 协调者更新 `.workflow/state.md`、卡片状态为 `accepted`、记录 runId 与证据路径。
- Git：**编写员**负责 commit（`feat(core): ...`）；协调者只做验收标记（tag 由编写员打，或协调者用 `git tag` 标记——tag 属元数据，不算代码工作）。
- 验收后立刻把"下一张卡"派给编写员，并把"已交卡"的回归测试入口留给测试员。

## 四、测试矩阵（测试员必用）

每个功能按类型勾选（勾选即必须实现，未勾选要写理由）：

| 维度 | 内容 | 触发条件 |
| :--- | :--- | :--- |
| 单元 | 纯函数逐分支、边界值、异常输入 | 总是 |
| 属性/模糊 | 随机输入下的不变量（幂等、往返、守恒、单调） | 解析器/序列化/ID/Patch/Diff |
| 契约 | 公共 API 与 CLI 的输出结构、退出码、错误码文案 | 总是 |
| 快照/黄金文件 | HTML 输出的结构稳定性（人工可审的黄金文件，不用巨型快照） | 生成器/渲染 |
| 集成 | 跨模块真实调用（磁盘 IO、真实文件、真实进程） | 总是 |
| 端到端 | 用户视角全流程（CLI 一条命令跑完、阅读器真实渲染） | 每个里程碑至少一次/功能 |
| 并发/时序 | 并行 patch、watcher 抖动、WS 断连重连、文件被外部改写 | Daemon/同步桥 |
| 崩溃/恢复 | 半写入文件、进程中途 kill、非法 JSON 元数据 | 持久化相关 |
| 性能 | 大文档（≥ 1MB HTML）耗时/内存预算 | AST/渲染/搜索 |
| 可访问性 | 键盘可达、对比度、语义标签 | 前端 |
| 安全 | XSS（注入 HTML/script/style）、路径穿越、原型污染、ReDoS | 总是（涉及输入即测） |
| 跨平台 | 路径分隔符、大小写、CRLF、非 ASCII 文件名 | 文件系统相关 |

**"不只是跑测试函数"** 的强制动作：
1. 黑盒实验：真实命令、真实文件、真实进程，记录命令与原始输出。
2. 破坏性实验：注入坏数据、截断文件、并发写、只读目录、超大节点、深层嵌套。
3. 反向验证：故意把实现改坏一行，确认测试会红（证明测试有效），再改回。
4. 变更前后对比：同一输入在旧/新实现下行为差异是否符合预期。

## 五、角色间通信协议

子会话之间**不能直接互相调用**。全部消息经协调者转发，落地为文件，保证可追溯：

```text
.workflow/
├── state.md                  # 单一事实来源：当前卡、门禁、runId、阈值计数
├── cards/<id>.md             # 功能卡
├── reports/
│   ├── impl-<card>.md        # 编写员交付（G1）
│   ├── audit-<card>.md       # 审计员报告（G2），含 P0/P1/P2
│   ├── test-<card>.md        # 测试员报告（G3）
│   └── verdict-<card>.md     # 协调者裁决（G4/G5）
└── handoffs/
    └── <role>-<n>.md         # 会话重生交接卡（见 §7）
```

消息格式（协调者转发时必须原样携带，不得改写技术细节）：

```text
FROM: auditor | TO: writer | CARD: M1.1 | SEVERITY: P1
FILE: packages/core/src/outline.ts:42
ISSUE: <一句话>
EVIDENCE: <命令/输出/推理>
REQUIRED: <期望的修复方向，不指定具体实现>
```

转发规则：
- P0 立即转发，不等其他报告。
- P1 汇总后一次转发，避免碎片化打断编写员。
- 审计员与测试员之间的交叉问题（例如测试员认为某 API 不可测），由协调者转给审计员评估契约设计。
- 每条消息在 `.workflow/state.md` 的"消息流水"里留一行记录（时间、方向、摘要、是否闭环）。

## 六、返工规则

1. 同一张卡最多 **3 轮**返工。第 3 轮仍有 P0/P1 → 升级给用户，附三轮证据与建议方案。
2. 返工只处理：审计 P0/P1 + 测试暴露的实现缺陷 + 测试自身的有效性缺陷。**不得顺手重构**（会引入不可审的 diff）。
3. 返工必须重跑**全量 CI**，不是只跑相关测试。
4. 同一 finding 第二次出现 → 判定为"设计问题"而非"手误"，由审计员升级为架构级 P1，编写员必须给出根因分析（写进报告），而不是再打补丁。
5. 测试员补测试导致实现必须变更时：测试员先出"期望行为"证据 → 协调者判定谁是错的（契约）→ 再派活。

## 七、上下文生命周期（ACP 阈值与重生）

三个会话都内置 ACP 压缩工具（`compress` / `decompress` / `search_context` / `acp_status`），必须主动使用：

### 7.1 阈值

- **软阈值 60%**：`acp_status` 显示上下文占用 ≥ 60% 时，角色应主动压缩已消费的探索/日志，保留结论。
- **重生阈值 150K tokens（≈ 15% 窗口）且"当前任务已完成"**：写交接卡 → 结束会话 → 由协调者开**全新会话**（`subagent` 新建 run，不 resume），把交接卡作为初始任务。
- **禁止**在任务中途清空/重生。任务未完成时只能压缩，不能失忆。
- **强制重生**：同一会话累计完成 ≥ 3 张卡后，即使未到阈值也建议重生，避免角色漂移与历史包袱。

### 7.2 交接卡格式（`.workflow/handoffs/<role>-<n>.md`）

```markdown
# HANDOFF <role> #<n> — <日期>

- 已完成的卡与结论: <card-id: 结论一句话>
- 已确立的约定/契约: <签名/路径/命名约定，逐条>
- 已知坑与教训: <tried X, failed because Y>
- 当前未完成事项: <如果为空，说明可以安全重生>
- 需要新会话先读的文件: <绝对路径列表，≤ 8 个>
- 不要重复做的探索: <一句话列表>
```

### 7.3 重生后的第一件事

新会话必须先读：交接卡 + 当前卡片 + `docs/04-engineering-standards.md`，然后**用自己的话复述**要做什么与验收标准，得到协调者确认后才动手。这防止积淀丢失。

## 八、升级给用户的情形（协调者不得自行决定）

- 涉及产品方向/优先级调整（里程碑变更）。

## 十、运行手册（已实测，2026-11-12）

### 10.1 会话如何创建

三个角色都是**独立 pi 进程的持久会话**，由协调者用 `subagent` 工具创建（`agent` + 自包含 `task`），用 `action: "resume"` + `id` 续接（同一会话保留历史，不必重述上下文）：

| 角色 | `subagent` agent | 工具 | 备注 |
| :--- | :--- | :--- | :--- |
| 编写员 | `worker` | read/edit/write/bash + ACP 压缩工具 | 唯一允许改源码的角色 |
| 审计员 | `reviewer` | read/grep/find/ls/watchdog_diff + ACP 压缩工具（**只读，无 bash/write**） | 报告正文回传，协调者落盘；命令核验由协调者/测试员代跑 |
| 测试员 | `worker` | read/edit/write/bash + ACP 压缩工具 | 通过任务卡硬性限定只能写 `tests/`、`*.test.ts`、`vitest.config.*` |

启动要点：
- 每个任务必须自带 `cwd`、`Scope`、`Out of scope`、验收标准、报告落盘路径（子会话看不到本会话上下文）。
- 新任务用 `subagent({ agent, task })`；续接用 `subagent({ action: "resume", id: "<runId>", message: "<本轮只做什么>" })`。每次 resume 会产生**新的 runId**，以最新为准并登记到 `state.md`。
- 三个会话的 runId 必须写在 `.workflow/state.md`，否则重启主会话后无法续接。
- **审计员报告没有落盘能力**：派 G2 时要在任务里写"报告正文回传，我会落盘"，收到后由协调者写入 `.workflow/reports/audit-<card>.md` 再转给编写员。

### 10.2 通信事实（已实测）

- 子会话之间**无法直接互调**（没有对方的 runId，也没有相互调用的工具）。所有跨角色信息走"报告文件 + 协调者转发"，这也是审计轨迹。
- 子会话**能看到彼此的文件**：实测审计员在测试员写测试文件期间就读到了它，并对测试质量下了 P1。这要求 §3.5 的"单写者"纪律：并行只允许"一个写者 + 若干只读"。
- 报告文件是最好的消息载体：`file:line` + 证据 + 要求方向，比自然语言转述更不容易失真。

### 10.3 ACP 压缩（已实测）

- 三个角色都实际调用了 `acp_status`；审计员在复审轮把上一轮 56 条消息压成 1 个块（`42.4K → 808`，约 56×），上下文回落到 5%。
- 因此 §7.1 的阈值是**可执行**的：角色按 `acp_status` 的占用率自主压缩，协调者只在"任务完成且达硬阈值"时执行重生。
- 实测数据点：一次完整"实现→审计→测试→返工→复审"循环后，各角色上下文约 5%–8%（1M 窗口）。按此推算，单会话可稳定承载 10+ 张卡，硬阈值 150K 有充足余量。

### 10.4 冒烟验证结论（能力自证）

在 `/tmp/hr-smoke` 用一张 `sumRange` 冒烟卡跑通全流程，验证了：

1. 编写员能写码、实跑自测、落盘报告、回报 ACP 状态。
2. 审计员能只读审计、独立复算反例、抓到 2 个 P0（`MAX_SAFE_INTEGER` 邻域精度失真、`start+end` 溢出产生 `Infinity`/`NaN`）与 5 个 P1，并**审计测试本身**（指出 todo 用例掩盖违约）。
3. 测试员能独立写测试、跑覆盖率、自建内存变异测试（10 个变异体）、完成 §6.3 全部攻击面，并明确回答"有没有办法引起 bug"。
4. 协调者转发后，编写员按 finding 返工；测试员**裁决测试与实现的冲突**（拒绝为绿灯删断言，改的是"锁定实现细节"的过时用例）；审计员复审给出 `CLOSED/PARTIAL` 逐条判定。
5. 复审结论为 `G4: FAIL`（1 个 P1 测试判别力不足）——证明门禁**不会**自动放行。

已知经验：
- 测试员容易写出"锁定实现细节"的断言（例：要求某溢出路径必须抛错，而新实现能给出精确值）。裁决必须以**规格**为准，且只由测试员改测试。
- 审计员的高价值产出来自"自己复算反例"，而不是读代码。任务卡里要显式要求"自己跑命令验证，不要相信报告"。
- **门禁命令不得与包管理器内建命令同名**：M1.0 实测，根脚本 `"ci"` 被 pnpm 自己的 `clean-install` 遮蔽，敲 `pnpm ci` 只重装依赖并 exit 0，形成假绿。聚合门禁统一命名 `verify`，入口 `pnpm verify`；CI workflow 内仍逐条显式执行以便定位。
- 子会话报告动辄 15–20KB，协调者只读结论段与 finding 标题，细节留在文件里，避免主会话膨胀。

## 十一、实战手册（M1.0–M1.5 期间累积的硬规则）

> 本节只收录**踩过坑**才写下的规则，每条都对应一次真实事故。新卡开工前，协调者把这节连同卡片一起发。

### 11.1 可读性与注释

1. **注释只解释签名表达不了的东西**：量级包络（"输入 ≤ 1MB 时 O(n)"）、精度承诺（"返回的双精度值在 ±2^53 内精确"）、抛错条件、与外部规范的对应关系（parse5 的 `startTag` 语义）。
2. **禁止"注释自我认证"**：`// 与直接写 href 同口径` 这类句子，如果实现与它不符，**按 P1 处理**——读者会当场被骗。
3. 模块头 ≤ 3 行：说清"这个文件负责哪一件事"，不复述导出的类型。

### 11.2 死代码即 P1

- 恒假的谓词、永远走不到的 `if`、`join(" ")` 之后又被归一化抹平的拼接，都属于"读起来像防护、实际上不存在"的代码。
- 覆盖率上不可达的分支**不许用 `/* v8 ignore */` 糊**，也不许用 `as` 断言绕过：优先**合并守卫**让唯一出口真实可达（M1.5 的 `parse.ts` 即如此），做不到就删掉那段防御。

### 11.3 列表与单值必须成对建例

- `<animate values='safe;javascript:alert(1)'>` 漏网事件（M1.5）的根因是"先净化再判"把列表拼回单个 token。
- 规则：凡代码里出现 `split(...).join(...)`、`replaceAll` 之后再比对的地方，审计员必须问一句 **"列表的第二个元素呢"**；测试员必须为每个"多值"属性同时构造单值与列表两组用例。
- 用例语料按 **`{元素} × {属性} × {单值 | 列表}`** 三维交叉建立，而不是按"攻击样例"手工挑。

### 11.4 裸异常 = P0

- 任何非 `HrError` 的抛出（`TypeError`/`RangeError`/`AggregateError`）从公开 API 漏出，一律 P0。
- 崩溃修复必须**同时**断言"不抛"与"子树/字节保真"：`<svg><template><circle/></template></svg>` 的往返断言比"不崩"更重要，否则会把"静默丢内容"写成绿灯。

### 11.5 签字轮也要报顺手发现

- 审计员核对单个 hunk 时撞到的既有缺陷，记为 `P*-Rn-k` 并注明"既有 / 非本次引入"，由协调者决定是否阻断当前卡。
- M1.5 收口时正是这样撞出 `<svg><template>` 裸崩（随机语料 1.3% 命中），比被签的那个改动危险得多。

### 11.6 fuzz 语料必须跨命名空间

- 4000 例随机标签串不含 `<svg>`+`<template>` 组合，就会得出"元素侧不可达"这种**弱证据结论**。
- fuzz 至少要覆盖 `foreign content（svg/math） × 特殊内容模型（template/table/select）` 的交叉。

### 11.7 并发与快照

- 编写员改 `src` 时，审计员**不得**以 `pnpm test` 作为唯一判据（它可能在跑别人的中间态）；审计员必须记录 `shasum` 前后一致，否则结论不对应同一份源码。
- 写者并发恒为 1：`src` 归编写员、`tests` 归测试员、配置归编写员，三者不重叠才允许并行。

### 11.8 提速口径（M1.6 起生效）

| 项 | 旧 | 新 |
| --- | --- | --- |
| 卡片粒度 | 一功能一卡 | 同文件族的相邻卡合并（M1.6+M1.7、M1.8+M1.9） |
| 审计轮 | G2-R 重跑全量 | G2-R 只验返工清单 + 1 个新攻击面 |
| P2 措辞类 | 阻塞提交 | 不阻塞，记入下一卡 |
| P0 / P1 / 覆盖率 | 零容忍 | **不变**：P0=0、P1=0、perFile 100% |

### 11.9 依赖策略（2026-11-14 用户裁定，取代"不新增任何依赖"）

旧规则"不新增任何依赖 / 一切零依赖手搓"**作废**。新规则：**按需引入成熟可靠的开源库**。

- 判定顺序：能用成熟库直接解决的问题，**优先用库**，不要手搓。手搓只保留在"库会引入更大风险"的场合（体积、许可、原生依赖、维护停滞）。
- **已经手搓出来的模块允许被替换**（例如 `annotations/diff.ts` 的手写 LCS）：走单独的重构卡，不夹在功能卡里。
- 两个执行边界：
  1. **前端运行时依赖**（`@hreader/app` 目前无 bundler）或**底层核心架构**替换（框架 / 打包器 / AST / 解析引擎）：先出选型方案（候选、体积、维护活跃度、替换成本、回退）给用户确认，再动手。
  2. Node 服务端与测试侧的轻量成熟库（HTTP 工具、diff、测试辅助、fuzz 生成器等）**可以自行引入**，无需逐次请示，但必须在卡片里登记"引了什么、为什么、替代了什么手搓代码"。
- **不许在未结的卡里推翻已过审代码**：当前卡先收口，替换另开一张重构卡，分批进行。
- 引入依赖时的门禁不变：`knip` 必须仍干净（不许有"装了没用"的依赖）、`dependency-cruiser` 的层次规则不得因新依赖破窗、`perFile` 四维 100% 不放宽。

### 11.10 测试与 CI 的执行纪律（2026-11-14，本机 OOM 事故后）

事故：16GB / 10 核机器上同时跑了 3 条完整流水线（我 + 编写员 + 测试员），每条都是 `tsc` + `esbuild` + vitest 线程池（≈9 worker）+ v8 覆盖率 + `depcruise` + `knip`，叠加到 60GB+ 虚拟占用，swap 打爆。

规则：
- **全量 `pnpm verify` 只有一个执行者：协调者**，且收口时只跑 1 次。任何角色（含我）跑之前先确认没有别的 vitest 在跑。
- 开发/返工期间只跑**定向命令**：`pnpm vitest run <单个测试文件>`、`eslint <改动文件>`、`tsc --noEmit`。禁止"边改边跑全量覆盖率"。
- `vitest.config.ts` 显式 `maxWorkers: 2`：这是**限流**，不是放宽门禁（`perFile: true` 四维 100% 不变）。
- 长命令一律**后台 + 轮询**：`(cmd > /tmp/v.log 2>&1; echo "EXIT=$?" >> /tmp/v.log) & sleep 45; tail /tmp/v.log`。前台静默 5 分钟会被 watchdog SIGKILL，而**它的子进程树不会被回收**——孤儿 `vitest`/`esbuild` 会继续吃内存，这是事故的第二个成因。
- 终止任何子代理后，立刻 `pkill -P <pid>` 并 `pgrep -fl "vitest|tsc|esbuild"` 确认无残留。
- 覆盖率红分两类，必须分开处置：**代码死**（该删/该合并守卫，P1）与**测试漏**（该补例）。判据是"哪条用户可见行为会触发它"，答不出来就按代码死处理。
