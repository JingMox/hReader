# hReader 四角色协作工作流 (Collaboration Workflow)

> [!IMPORTANT]
> 本文档是 hReader 项目的**协作契约**。它定义了协调者（主会话）与四个执行角色（编写员 / 测试编写员 / 审计员 / 测试员）的职责边界、交付物、门禁（Gate）、通信协议、返工规则与上下文生命周期。
>
> **2026-11-19 用户裁定（四角色）**：测试代码**不再由业务编写员写**，改由**独立的测试编写员**写，出发点必须是「攻击这个功能」而不是「跟随实现」。业务代码与测试代码的作者不同人，测试员再从外部攻击两者。理由见 §11.55（M4.7 结卡后试用撞到的两个入门坑，2974 例、四维 100%、变异 16 KILLED 全绿也没抓到）。
>
> 任何角色在任何时候都不得越过本文档规定的边界。规则冲突时，以本文档 + [04-engineering-standards.md](04-engineering-standards.md) 为准；仍冲突则升级给用户裁决。

## 一、角色总览

| 角色 | 技术载体 | 工具权限 | 写入范围 | 一句话职责 |
| :--- | :--- | :--- | :--- | :--- |
| **协调者**（主会话，用户直连） | 主 Pi 会话 | 全部 | 仅 `docs/`、`.workflow/` | 拆卡、派活、转发消息、裁决、验收。**不写任何产品代码，不跑实现类命令** |
| **编写员** (Writer，业务) | `subagent` 工具，`worker` 角色，独立会话 | read / edit / write / bash | `packages/**/src/**`、`packages/**/package.json`、构建与 CI 配置、`styles/**`、`skills/**`。**`packages/**/tests/**` 只读**（见 §1.2） | 实现功能、写配置、修 P0/P1、写实现报告。**不写测试** |
| **测试编写员** (Test-Writer) | `subagent` 工具，`worker` 角色，独立会话 | read / edit / write / bash | **只写** `packages/**/tests/**`、`packages/**/e2e/**`、`scripts/**/*test*` | 独立写测试代码，出发点是**攻击功能**：从用户旅程、公开契约、失败模式出发反推用例 |
| **审计员** (Auditor) | `subagent` 工具，`reviewer` 角色，独立会话，**纯只读（无 `bash` / `write`）** | read / grep / find / ls / watchdog_diff | **无写权限**：报告以正文回传，由协调者落盘到 `.workflow/reports/audit-<card>.md` | 审计代码与测试质量，输出可执行的 P0/P1/P2 清单 |
| **测试员** (Tester) | `subagent` 工具，`worker` 角色，独立会话，**纯只读（不写仓库文件）** | read / edit / write / bash（只用于 `/tmp` 副本与真产物探针） | **无仓库写权限**：用例归测试编写员（§1.2b）；测试员交攻击计划、攻击向量、变异结果 | 从外部攻击实现**和**用例、独立验证、判用例是否守得住、写测试报告 |

> **角色载体（2026-11-14 起）**：子代理由 `pi-subagents` 插件提供（`subagent` 工具），续接用 `action: "resume"`；旧的 `acp_delegate` / `resumeFrom` 写法作废。`reviewer` 角色**没有 `bash` 与 `write`**，因此：①审计员不能自己落盘报告——它把报告正文回传，协调者写进 `.workflow/reports/audit-<card>.md`；②审计员不能自己跑命令核验——它把"要跑什么、期望看到什么"写成"待核验命令"，由协调者或测试员执行并回贴输出。这是权限换来的可审计性，不是效率损失。
>
> 三个子代理角色统一 `thinking: low`（`~/.pi/agent/settings.json` 的 `subagents.agentOverrides`），主会话保持 `high`。派单时若传 `model` 参数，必须带 `:low` 后缀，否则会覆盖掉该默认。

### 1.1 协调者（主会话）—— 只做协调，不写代码

允许做的事：
- 读取代码/文档用于**判断**（review 结果、定位问题、写任务卡）。
- 拆解功能卡、写/更新 `.workflow/` 状态与报告、转发角色间的消息。
- 裁决冲突、控制返工轮次、执行最终验收（`git` 提交与打 tag 除外——见 §3.6）。
- 用只读手段验证"证据真实性"（例如抽查审计员引用的 `file:line` 是否存在）。

禁止做的事：
- 修改任何 `packages/**`、`styles/**`、`skills/**` 下的产品代码或配置。
- 代替编写员实现功能（**含测试代码**）、代替测试员设计攻击面、代替审计员下结论。
- 因为"子会话太慢"而自己动手。慢就等，或换更快的模型档位。

### 1.2 编写员 (Writer)

职责：
- 按功能卡实现。范围严格限定在卡片的 `Scope` 内，发现必须扩大范围时**停下来报告**，不得擅自扩张。
- 保持 [04-engineering-standards.md](04-engineering-standards.md) 的全部硬性要求（可读性、注释规约、裸类型 API、架构边界）。
- 自测：至少证明"功能在真实路径上跑通一次"（CLI 实跑 / 真实文件读写），再交卡。**自测靠跑真实命令，不靠跑你自己写的用例——本卡的用例不是你写的。**
- 开发期间只跑**单文件定向测试**（`pnpm vitest run <单个测试文件>`）与改动文件的 `eslint` / `tsc --noEmit`；**全量 `pnpm verify` 由协调者在收口时跑 1 次**（见 §3.6 与 §11.10）。
- 交卡时必须附：定向测试的真实输出 + "哪些改动没被定向测试覆盖、为什么"。
- 处理审计员与测试员提出的 P0/P1；P2 可排期但必须在卡片里登记。
- **硬边界：不得新增/修改/删除 `packages/**/tests/**` 下的任何文件**。测试归测试编写员（§1.2b）。你可以**读**测试来理解既有契约，但改了就是串味——同源写测试正是 M4.7 之后被用户否掉的做法（§11.55）。
- 如果发现某个既有用例因为你的改动而必须调整，**停下来报告**：写清「哪条用例、为什么它锁住了实现细节、建议改成什么」，由协调者转测试编写员改。
- 你不"拥有"测试的判定权：判定代码守不守得住的是测试编写员（用例）、测试员（攻击）与审计员（代码与用例的双向审计）。

### 1.2b 测试编写员 (Test-Writer)

职责：
- **只为攻击写测试**。拿到卡片的 `用户可见行为` + `AC` + 公开契约（`--help` 输出、HTTP 路由表、UI 行为、文件格式），在**不读实现细节**的前提下设计用例：先写「用户会怎么用错它」，再写「正确用法」，最后写「实现最可能在哪漏水」。
- **禁止以 `src/` 为出发点**：可以读 `src/` 只为确认**公开契约**（导出签名、错误码、CLI 选项），**不得**照抄实现的分支结构来排用例（那是「顺着代码测」，M1–M4 全周期的通病）。判定标准：把这批用例交给一个没看过 `src/` 的人，他只看用例名能否说出功能该干什么。
- **首用路径必写**（§4 的 journey 维度）：从**空目录**开始，只用文档与 `--help`，把功能跑到产物；任何一步打印出来的地址/命令，都要**照着它执行**一次（不是正则匹配它的形状）。
- **攻击面必写**：坏输入、截断/半写文件、并发、重复执行幂等、超长/Unicode/CRLF、权限、路径穿越、注入、资源泄漏（句柄/定时器/子进程）、以及「实现者最不可能手工验的那条」。
- **不写业务代码**：`packages/**/src/**` 只读。发现实现缺陷登记给协调者，不修。
- 自查一条硬要求：**每条新用例都要能说出「把实现改坏成什么样，它会红」**。说不出就是装饰，删掉或改写。
- 交卡附：新增/改动用例清单（文件名 + 用例名 + 它守的是哪条 AC 或哪个攻击面）+ 定向运行的真实输出。

### 1.3 审计员 (Auditor)

职责：
- 审计代码：可读性、命名、注释是否只解释"签名表达不了的东西"、裸类型 API 是否被包装类污染、封装与模块边界、错误处理、边界条件、性能陷阱、跨平台路径、安全性（HTML 注入 / 路径穿越 / 原型污染）。
- 审计架构：职责是否单一、依赖方向是否单向、公开 API 面是否最小、是否存在隐式全局状态。
- 审计**测试本身**：同义反复断言、过度 mock、只断言不验证、快照倾倒、缺负路径、缺并发/错误路径、测试是否真的能抓到 bug（变异测试结果的可信度）。
- 输出 finding：`P0`（阻断：错误行为/安全隐患/架构破窗）、`P1`（必须本卡修复：可读性差、契约不清、测试薄弱）、`P2`（可排期）。每条必须带 `path:line`、复现/推理、要求的修复方向。
- **只读**。`reviewer` 没有 `bash`/`write`：不许改代码，也不能自己落盘。报告以**正文**回传，协调者写入 `.workflow/reports/audit-<card>.md`。
- 需要跑命令才能定的结论，写成"待核验命令"（完整命令行 + 期望输出 + 若不符则说明什么），由协调者或测试员执行并把真实输出回贴给你。
- 结论必须能落到 `path:line`；读不到的结论标 `UNVERIFIED`，不许用"通常/大概"代替证据。

### 1.4 测试员 (Tester)

职责：
- 为每张卡建立**测试计划**（先写计划再写断言），覆盖 §4 的多角度矩阵。
- **不写仓库文件**：用例归测试编写员（§1.2b）。你交的是**攻击计划 + 攻击结论**（场景 / 期望的可观察输出 / 若实现错了这条会怎么红 / 实测是否红了）。你自己在 `/tmp` 副本与真实产物上写一次性探针。
- **双向攻击**：既要攻击**实现**，也要攻击**测试编写员写的用例**——找哪些断言恒真、哪些用例只覆盖 happy path、哪些「测的是实现的自述而不是行为」、哪些路径整批用例都没碰（用 `grep` 找「该有却没有的用例」，而不是只审已有用例）。
- 做**功能外对抗实验**：不使用测试函数，而是像用户/攻击者一样从黑盒角度尝试打坏它（真实 CLI 调用、坏输入、超大输入、编码/换行/路径边界、并发、断电式中断、重复执行幂等性）。
- 回答一个明确的问题：**"有没有办法引起这个功能的 bug？"** 必须给出结论 + 尝试过的手段清单 + 未覆盖的风险。
- 发现实现缺陷时**不修源码**，登记到报告并交协调者转编写员。
- 审**测试编写员**落地的用例：**弱断言**（两臂都能过、子串匹配、只断言"没抛错"）逐条点出，判它是否锁得住行为与来源；并清点「该有用例却没有」的入口（§4 第 5 条）。
- 输出 `.workflow/reports/test-<card>.md`，包含：测试矩阵、执行的命令、实际输出摘录、覆盖率、变异分数、弱断言清单、未覆盖风险。

## 二、工作单元：功能卡 (Feature Card)

一切工作以卡片为单位。卡片由协调者创建，存放在 `.workflow/cards/<card-id>.md`，格式：

```markdown
# CARD <id> — <标题>

- 里程碑: M1 / M2 / M3 / M4
- 依赖: <card-id 或 无>
- 状态: todo | implementing | auditing | testing | rework | accepted | blocked
- Scope(写): 允许修改的路径（白名单）
- Out of scope: 明确不做的事
- 用户可见行为: 一段话，能当作验收脚本
- 验收标准 (AC): 编号列表，可机械判定
- 契约: 公共 API 签名 / CLI 输出 / 文件格式（裸类型，见 04 文档）
- 风险点: 已知的坑与需要特别审计的地方
```

卡片拆分原则：单卡应能在**一次编写员会话内**完成；单卡新增/修改源码建议 ≤ 400 行；跨包改造必须拆卡。

## 三、门禁 (Gates) 与流程

```text
G0 拆卡(协调者)
   → G1a 实现(编写员)  ─────────────────────────┐  两条独立路径，作者不同人
   → G1b 写测试(测试编写员，与 G1a 并行/紧随)   │  且互不读对方的工作区改动
        ↓                                      │
   → G2 审计(审计员) ─┐（并行，只读，审代码＋审用例）│ 全量CI绿 + 双方自测证据
   → G3 测试(测试员) ─┘（并行，只读/探针，攻击实现＋攻击用例）
        ↓                                      │
   G4 裁决(协调者): 无P0/P1 且 测试全绿 且 覆盖/变异/首用路径达标 ?
        ├─ 否 → G4' 返工(谁的问题谁改：业务→编写员，用例→测试编写员) → 复审 → G4（最多 3 轮）
        └─ 是 → G5 验收(协调者): 更新 state、打 tag、记录卡片 accepted → 下一张卡
```

### 3.1 G0 — 拆卡（协调者）

- 从 [02-architecture-and-roadmap.md](02-architecture-and-roadmap.md) 的里程碑任务拆出卡片。
- 卡片必须写清 `Scope` 与 `Out of scope`；没有 Scope 不许开工。
- 一次只推进**一张**卡（串行推进，避免多写者冲突）。允许"实现 A 卡的同时，为已交卡的 B 卡做审计/测试"，但同一时刻仓库里**只能有一个写者**。

### 3.2 G1a — 实现（编写员）

交付物（缺一不可）：
1. 变更代码 + 必要的配置（**不含任何 `tests/**` 改动**）。
2. 全量 `pnpm verify` 全绿输出（**收口时由协调者跑**，贴 tail 摘要含各步骤 PASS；开发期间用定向测试代替）。
3. 自测证据：真实命令 + 真实输出（不是"单元测试通过"）。
4. 变更说明：做了什么、为什么这样设计、有没有偏离卡片契约。
5. 一个 commit（见 §3.6）。

### 3.2b G1b — 写测试（测试编写员）

- 输入：卡片 `用户可见行为` + `AC` + 公开契约。**输入里没有 `git diff`**——本轮实现长什么样与本角色无关（要读也只读导出签名与错误码）。
- 交付物：①新增/改动用例（文件名 + 用例名 + 守的 AC/攻击面）；②定向运行输出；③**攻击面清单**：写清「我试过打坏它的 N 种方式，其中哪些已经被用例钉住、哪些钉不住要交给测试员」。
- 与 G1a 冲突时（实现和用例对不上）：**不改实现**，把冲突写成「用例期望 X，实现给 Y，契约是 Z」交协调者裁决。
- 判据自检：每条用例都能说出「实现怎么变坏它就红」；说不出就删。

### 3.3 G2 — 审计（审计员）

- 输入：卡片 + `git show --stat`/`git diff` + 全量 CI 结果。
- 必须逐条回答卡片 `AC`：每条 AC 是否有代码/测试支撑，支撑是否真实。
- 必须给出：`P0/P1/P2` 清单（可为空，但要写"我检查了 X/Y/Z，未发现问题"的检查项清单，防止空转）。
- 必查清单（每次都要过一遍）：命名与可读性、注释是否复述代码、裸类型契约、错误路径、边界（空/超大/Unicode/CRLF/路径穿越）、并发与重入、资源释放、跨平台、公开 API 面、依赖方向、测试有效性。

### 3.4 G3 — 测试（测试员）

- 先交**攻击计划**（矩阵 + 攻击面 + 「该有用例却缺失」的清单），再交**攻击结论**：对实现做了什么、对测试编写员的用例做了什么、哪些用例被你的探针打穿。
- **必答两问**：①「有没有办法引起这个功能的 bug？」②「**有没有办法让这批用例全绿而功能是坏的？**」——第二问是本轮新增的硬门槛（M4.7 的教训：用例全绿 + 变异全杀，仍可能整条用户路径走不通）。
- 硬性门槛（未达标即 G4 失败）：
  - 全量 CI 绿。
  - 行/分支/函数/语句覆盖率 ≥ **90%**（核心 `packages/core` ≥ **95%**）。
  - 关键纯逻辑（解析器、ID 生成、Patch 计算、Outline 提取）跑**变异测试**，mutation score ≥ **75%**。
  - 至少 1 个"用户视角黑盒实验"（真实 CLI/真实文件/真实浏览器）。
  - 至少 1 个负路径 × 每类错误（不存在的文件、非法 HTML、非法 selector、超长输入、权限不足）。
- 报告必须能给协调者直接判卷：命令可复制、输出可核对、结论明确。

### 3.5 G4 — 裁决（协调者）

**门禁前置（2026-11-15 起）**：编写员每交一批（一个 `F` 编号），协调者**先跑一次全量 `pnpm verify`**，
红了立刻退回返工，**再**派审计与测试。理由（M3.1.1 实测）：定向命令的覆盖面不足以保证门禁绿——
`vitest run <单文件>` + `tsc --noEmit` + `eslint <改动文件>` 全绿，全量仍可能红（该轮红在
`packages/core/tests/io/facade.test.ts:35`：公开导出面除根 barrel 外还有一处精确拼写）。
而按 §10.9，审计员与测试员都不跑全量，所以"最后一公里"的红只有协调者能发现；前置跑一次，
把"两路复核之后才发现红"变成"退回时不浪费两路复核"。

通过条件（全部满足）：
- 审计：无 P0，无未处理的 P1。
- 测试：CI 绿 + 覆盖率/变异达标 + 无 P0/P1 缺陷。
- 卡片 `AC` 逐条有证据。
- 无越界修改（`git diff --stat` 范围与 `Scope` 一致）。

不通过 → 返工，规则见 §6。

### 3.6 G5 — 验收与提交

- 协调者更新 `.workflow/state.md`、卡片状态为 `accepted`、记录 runId 与证据路径。
- Git：**编写员**负责 commit（`feat(core): ...`）；协调者只做验收标记（tag 由编写员打，或协调者用 `git tag` 标记——tag 属元数据，不算代码工作）。
- 验收后立刻把"下一张卡"派给编写员，并把"已交卡"的回归测试入口留给测试员。

## 四、测试矩阵（测试员必用）

每个功能按类型勾选（勾选即必须实现，未勾选要写理由）：

| 维度 | 内容 | 触发条件 |
| :--- | :--- | :--- |
| 单元 | 纯函数逐分支、边界值、异常输入 | 总是 |
| 属性/模糊 | 随机输入下的不变量（幂等、往返、守恒、单调） | 解析器/序列化/ID/Patch/Diff |
| 契约 | 公共 API 与 CLI 的输出结构、退出码、错误码文案 | 总是 |
| 快照/黄金文件 | HTML 输出的结构稳定性（人工可审的黄金文件，不用巨型快照） | 生成器/渲染 |
| 集成 | 跨模块真实调用（磁盘 IO、真实文件、真实进程） | 总是 |
| 端到端 | 用户视角全流程（CLI 一条命令跑完、阅读器真实渲染） | 每个里程碑至少一次/功能 |
| **首用路径 (journey)** | **从空目录、只凭 `--help` 与文档**走到产物；打印出的地址/命令**照着执行**（不是正则匹配形状） | **总是（缺此维度即 G4 失败）** |
| 并发/时序 | 并行 patch、watcher 抖动、WS 断连重连、文件被外部改写 | Daemon/同步桥 |
| 崩溃/恢复 | 半写入文件、进程中途 kill、非法 JSON 元数据 | 持久化相关 |
| 性能 | 大文档（≥ 1MB HTML）耗时/内存预算 | AST/渲染/搜索 |
| 可访问性 | 键盘可达、对比度、语义标签 | 前端 |
| 安全 | XSS（注入 HTML/script/style）、路径穿越、原型污染、ReDoS | 总是（涉及输入即测） |
| 跨平台 | 路径分隔符、大小写、CRLF、非 ASCII 文件名 | 文件系统相关 |

**"不只是跑测试函数"** 的强制动作：
1. 黑盒实验：真实命令、真实文件、真实进程，记录命令与原始输出。
2. 破坏性实验：注入坏数据、截断文件、并发写、只读目录、超大节点、深层嵌套。
3. 反向验证：故意把实现改坏一行，确认测试会红（证明测试有效），再改回。
4. **可发现性验证**：凡是程序打印给用户的路径（URL / 命令 / 文件位置），必须有一条测试**照它执行**并成功；只断言字符串形状的用例记为弱断言。
5. **缺失面清点**：`grep` 出功能声明的入口（CLI 子命令、HTTP 路由、MCP 工具、UI 交互），逐个确认「有没有一条用例从用户入口走到它」。有入口无用例 = 假覆盖（`injectNodeIds` 100% 覆盖但用户无法调用，见 §11.55）。
4. 变更前后对比：同一输入在旧/新实现下行为差异是否符合预期。

## 五、角色间通信协议

子会话之间**不能直接互相调用**。全部消息经协调者转发，落地为文件，保证可追溯：

```text
.workflow/
├── state.md                  # 单一事实来源：当前卡、门禁、runId、阈值计数
├── cards/<id>.md             # 功能卡
├── reports/
│   ├── impl-<card>.md        # 编写员交付（G1）
│   ├── audit-<card>.md       # 审计员报告（G2），含 P0/P1/P2
│   ├── test-<card>.md        # 测试员报告（G3）
│   └── verdict-<card>.md     # 协调者裁决（G4/G5）
└── handoffs/
    └── <role>-<n>.md         # 会话重生交接卡（见 §7）
```

消息格式（协调者转发时必须原样携带，不得改写技术细节）：

```text
FROM: auditor | TO: writer | CARD: M1.1 | SEVERITY: P1
FILE: packages/core/src/outline.ts:42
ISSUE: <一句话>
EVIDENCE: <命令/输出/推理>
REQUIRED: <期望的修复方向，不指定具体实现>
```

转发规则：
- P0 立即转发，不等其他报告。
- P1 汇总后一次转发，避免碎片化打断编写员。
- 审计员与测试员之间的交叉问题（例如测试员认为某 API 不可测），由协调者转给审计员评估契约设计。
- 每条消息在 `.workflow/state.md` 的"消息流水"里留一行记录（时间、方向、摘要、是否闭环）。

## 六、返工规则

1. 同一张卡最多 **3 轮**返工。第 3 轮仍有 P0/P1 → 升级给用户，附三轮证据与建议方案。
2. 返工只处理：审计 P0/P1 + 测试暴露的实现缺陷 + 测试自身的有效性缺陷。**不得顺手重构**（会引入不可审的 diff）。
3. 返工必须重跑**全量 CI**，不是只跑相关测试。
4. 同一 finding 第二次出现 → 判定为"设计问题"而非"手误"，由审计员升级为架构级 P1，编写员必须给出根因分析（写进报告），而不是再打补丁。
5. 测试员补测试导致实现必须变更时：测试员先出"期望行为"证据 → 协调者判定谁是错的（契约）→ 再派活。

## 七、上下文生命周期（ACP 阈值与重生）

三个会话都内置 ACP 压缩工具（`compress` / `decompress` / `search_context` / `acp_status`），必须主动使用：

### 7.1 阈值

- **软阈值 60%**：`acp_status` 显示上下文占用 ≥ 60% 时，角色应主动压缩已消费的探索/日志，保留结论。
- **重生阈值 150K tokens（≈ 15% 窗口）且"当前任务已完成"**：写交接卡 → 结束会话 → 由协调者开**全新会话**（`subagent` 新建 run，不 resume），把交接卡作为初始任务。
- **禁止**在任务中途清空/重生。任务未完成时只能压缩，不能失忆。
- **强制重生**：同一会话累计完成 ≥ 3 张卡后，即使未到阈值也建议重生，避免角色漂移与历史包袱。

### 7.2 交接卡格式（`.workflow/handoffs/<role>-<n>.md`）

```markdown
# HANDOFF <role> #<n> — <日期>

- 已完成的卡与结论: <card-id: 结论一句话>
- 已确立的约定/契约: <签名/路径/命名约定，逐条>
- 已知坑与教训: <tried X, failed because Y>
- 当前未完成事项: <如果为空，说明可以安全重生>
- 需要新会话先读的文件: <绝对路径列表，≤ 8 个>
- 不要重复做的探索: <一句话列表>
```

### 7.3 重生后的第一件事

新会话必须先读：交接卡 + 当前卡片 + `docs/04-engineering-standards.md`，然后**用自己的话复述**要做什么与验收标准，得到协调者确认后才动手。这防止积淀丢失。

## 十、运行手册（已实测，2026-11-12）

### 10.1 会话如何创建

三个角色都是**独立 pi 进程的持久会话**，由协调者用 `subagent` 工具创建（`agent` + 自包含 `task`），用 `action: "resume"` + `id` 续接（同一会话保留历史，不必重述上下文）：

| 角色 | `subagent` agent | 工具 | 备注 |
| :--- | :--- | :--- | :--- |
| 编写员 | `worker` | read/edit/write/bash + ACP 压缩工具 | 唯一允许改源码的角色 |
| 审计员 | `reviewer` | read/grep/find/ls/watchdog_diff + ACP 压缩工具（**只读，无 bash/write**） | 报告正文回传，协调者落盘；命令核验由协调者/测试员代跑 |
| 测试员 | `worker` | read/edit/write/bash + ACP 压缩工具 | 只写 `/tmp` 副本与探针脚本；**仓库文件由编写员写** |

启动要点：
- 每个任务必须自带 `cwd`、`Scope`、`Out of scope`、验收标准、报告落盘路径（子会话看不到本会话上下文）。
- 新任务用 `subagent({ agent, task })`；续接用 `subagent({ action: "resume", id: "<runId>", message: "<本轮只做什么>" })`。每次 resume 会产生**新的 runId**，以最新为准并登记到 `state.md`。
- 三个会话的 runId 必须写在 `.workflow/state.md`，否则重启主会话后无法续接。
- **审计员报告没有落盘能力**：派 G2 时要在任务里写"报告正文回传，我会落盘"，收到后由协调者写入 `.workflow/reports/audit-<card>.md` 再转给编写员。

### 10.2 通信事实（已实测）

- 子会话之间**无法直接互调**（没有对方的 runId，也没有相互调用的工具）。所有跨角色信息走"报告文件 + 协调者转发"，这也是审计轨迹。
- 子会话**能看到彼此的文件**：实测审计员在测试员写测试文件期间就读到了它，并对测试质量下了 P1。这要求 §3.5 的"单写者"纪律：并行只允许"一个写者 + 若干只读"。
- 报告文件是最好的消息载体：`file:line` + 证据 + 要求方向，比自然语言转述更不容易失真。

### 10.3 ACP 压缩（已实测）

- 三个角色都实际调用了 `acp_status`；审计员在复审轮把上一轮 56 条消息压成 1 个块（`42.4K → 808`，约 56×），上下文回落到 5%。
- 因此 §7.1 的阈值是**可执行**的：角色按 `acp_status` 的占用率自主压缩，协调者只在"任务完成且达硬阈值"时执行重生。
- 实测数据点：一次完整"实现→审计→测试→返工→复审"循环后，各角色上下文约 5%–8%（1M 窗口）。按此推算，单会话可稳定承载 10+ 张卡，硬阈值 150K 有充足余量。

### 10.4 冒烟验证结论（能力自证）

在 `/tmp/hr-smoke` 用一张 `sumRange` 冒烟卡跑通全流程，验证了：

1. 编写员能写码、实跑自测、落盘报告、回报 ACP 状态。
2. 审计员能只读审计、独立复算反例、抓到 2 个 P0（`MAX_SAFE_INTEGER` 邻域精度失真、`start+end` 溢出产生 `Infinity`/`NaN`）与 5 个 P1，并**审计测试本身**（指出 todo 用例掩盖违约）。
3. 测试员能独立写测试、跑覆盖率、自建内存变异测试（10 个变异体）、完成 §6.3 全部攻击面，并明确回答"有没有办法引起 bug"。
4. 协调者转发后，编写员按 finding 返工；测试员**裁决测试与实现的冲突**（拒绝为绿灯删断言，改的是"锁定实现细节"的过时用例）；审计员复审给出 `CLOSED/PARTIAL` 逐条判定。
5. 复审结论为 `G4: FAIL`（1 个 P1 测试判别力不足）——证明门禁**不会**自动放行。

已知经验：
- 测试员容易写出"锁定实现细节"的断言（例：要求某溢出路径必须抛错，而新实现能给出精确值）。裁决必须以**规格**为准，且只由测试员改测试。
- 审计员的高价值产出来自"自己复算反例"，而不是读代码。任务卡里要显式要求"自己跑命令验证，不要相信报告"。
- **门禁命令不得与包管理器内建命令同名**：M1.0 实测，根脚本 `"ci"` 被 pnpm 自己的 `clean-install` 遮蔽，敲 `pnpm ci` 只重装依赖并 exit 0，形成假绿。聚合门禁统一命名 `verify`，入口 `pnpm verify`；CI workflow 内仍逐条显式执行以便定位。
- 子会话报告动辄 15–20KB，协调者只读结论段与 finding 标题，细节留在文件里，避免主会话膨胀。

## 十一、实战手册（M1.0–M1.5 期间累积的硬规则）

> 本节只收录**踩过坑**才写下的规则，每条都对应一次真实事故。新卡开工前，协调者把这节连同卡片一起发。

### 11.1 可读性与注释

1. **注释只解释签名表达不了的东西**：量级包络（"输入 ≤ 1MB 时 O(n)"）、精度承诺（"返回的双精度值在 ±2^53 内精确"）、抛错条件、与外部规范的对应关系（parse5 的 `startTag` 语义）。
2. **禁止"注释自我认证"**：`// 与直接写 href 同口径` 这类句子，如果实现与它不符，**按 P1 处理**——读者会当场被骗。
3. 模块头 ≤ 3 行：说清"这个文件负责哪一件事"，不复述导出的类型。

### 11.2 死代码即 P1

- 恒假的谓词、永远走不到的 `if`、`join(" ")` 之后又被归一化抹平的拼接，都属于"读起来像防护、实际上不存在"的代码。
- 覆盖率上不可达的分支**不许用 `/* v8 ignore */` 糊**，也不许用 `as` 断言绕过：优先**合并守卫**让唯一出口真实可达（M1.5 的 `parse.ts` 即如此），做不到就删掉那段防御。

### 11.3 列表与单值必须成对建例

- `<animate values='safe;javascript:alert(1)'>` 漏网事件（M1.5）的根因是"先净化再判"把列表拼回单个 token。
- 规则：凡代码里出现 `split(...).join(...)`、`replaceAll` 之后再比对的地方，审计员必须问一句 **"列表的第二个元素呢"**；测试员必须为每个"多值"属性同时构造单值与列表两组用例。
- 用例语料按 **`{元素} × {属性} × {单值 | 列表}`** 三维交叉建立，而不是按"攻击样例"手工挑。

### 11.4 裸异常 = P0

- 任何非 `HrError` 的抛出（`TypeError`/`RangeError`/`AggregateError`）从公开 API 漏出，一律 P0。
- 崩溃修复必须**同时**断言"不抛"与"子树/字节保真"：`<svg><template><circle/></template></svg>` 的往返断言比"不崩"更重要，否则会把"静默丢内容"写成绿灯。

### 11.5 签字轮也要报顺手发现

- 审计员核对单个 hunk 时撞到的既有缺陷，记为 `P*-Rn-k` 并注明"既有 / 非本次引入"，由协调者决定是否阻断当前卡。
- M1.5 收口时正是这样撞出 `<svg><template>` 裸崩（随机语料 1.3% 命中），比被签的那个改动危险得多。

### 11.6 fuzz 语料必须跨命名空间

- 4000 例随机标签串不含 `<svg>`+`<template>` 组合，就会得出"元素侧不可达"这种**弱证据结论**。
- fuzz 至少要覆盖 `foreign content（svg/math） × 特殊内容模型（template/table/select）` 的交叉。

### 11.7 并发与快照

- 编写员改 `src` 时，审计员**不得**以 `pnpm test` 作为唯一判据（它可能在跑别人的中间态）；审计员必须记录 `shasum` 前后一致，否则结论不对应同一份源码。
- 写者并发恒为 1：`src` 归编写员、`tests` 归测试员、配置归编写员，三者不重叠才允许并行。

### 11.8 提速口径（M1.6 起生效）

| 项 | 旧 | 新 |
| --- | --- | --- |
| 卡片粒度 | 一功能一卡 | 同文件族的相邻卡合并（M1.6+M1.7、M1.8+M1.9） |
| 审计轮 | G2-R 重跑全量 | G2-R 只验返工清单 + 1 个新攻击面 |
| P2 措辞类 | 阻塞提交 | 不阻塞，记入下一卡 |
| P0 / P1 / 覆盖率 | 零容忍 | **不变**：P0=0、P1=0、perFile 100% |

### 11.9 依赖策略（2026-11-14 用户裁定，取代"不新增任何依赖"）

旧规则"不新增任何依赖 / 一切零依赖手搓"**作废**。新规则：**按需引入成熟可靠的开源库**。

- 判定顺序：能用成熟库直接解决的问题，**优先用库**，不要手搓。手搓只保留在"库会引入更大风险"的场合（体积、许可、原生依赖、维护停滞）。
- **已经手搓出来的模块允许被替换**（例如 `annotations/diff.ts` 的手写 LCS）：走单独的重构卡，不夹在功能卡里。
- 两个执行边界：
  1. **前端运行时依赖**（`@hreader/app` 目前无 bundler）或**底层核心架构**替换（框架 / 打包器 / AST / 解析引擎）：先出选型方案（候选、体积、维护活跃度、替换成本、回退）给用户确认，再动手。
  2. Node 服务端与测试侧的轻量成熟库（HTTP 工具、diff、测试辅助、fuzz 生成器等）**可以自行引入**，无需逐次请示，但必须在卡片里登记"引了什么、为什么、替代了什么手搓代码"。
- **不许在未结的卡里推翻已过审代码**：当前卡先收口，替换另开一张重构卡，分批进行。
- 引入依赖时的门禁不变：`knip` 必须仍干净（不许有"装了没用"的依赖）、`dependency-cruiser` 的层次规则不得因新依赖破窗、`perFile` 四维 100% 不放宽。

### 11.10 测试与 CI 的执行纪律（2026-11-14，本机 OOM 事故后）

事故：16GB / 10 核机器上同时跑了 3 条完整流水线（我 + 编写员 + 测试员），每条都是 `tsc` + `esbuild` + vitest 线程池（≈9 worker）+ v8 覆盖率 + `depcruise` + `knip`，叠加到 60GB+ 虚拟占用，swap 打爆。

规则：
- **全量 `pnpm verify` 只有一个执行者：协调者**，且收口时只跑 1 次。任何角色（含我）跑之前先确认没有别的 vitest 在跑。
- 开发/返工期间只跑**定向命令**：`pnpm vitest run <单个测试文件>`、`eslint <改动文件>`、`tsc --noEmit`。禁止"边改边跑全量覆盖率"。
- `vitest.config.ts` 显式 `maxWorkers: 2`：这是**限流**，不是放宽门禁（`perFile: true` 四维 100% 不变）。
- 长命令一律**后台 + 轮询**：`(cmd > /tmp/v.log 2>&1; echo "EXIT=$?" >> /tmp/v.log) & sleep 45; tail /tmp/v.log`。前台静默 5 分钟会被 watchdog SIGKILL，而**它的子进程树不会被回收**——孤儿 `vitest`/`esbuild` 会继续吃内存，这是事故的第二个成因。
- 终止任何子代理后，立刻 `pkill -P <pid>` 并 `pgrep -fl "vitest|tsc|esbuild"` 确认无残留。
- 覆盖率红分两类，必须分开处置：**代码死**（该删/该合并守卫，P1）与**测试漏**（该补例）。判据是"哪条用户可见行为会触发它"，答不出来就按代码死处理。

### 11.11 契约瘦身与"零消费字段"三分法（C1，2026-11-14）

**背景**：M2.3 收口时发现 diff 响应体里 `reason` 与 `originNodeId` 两个字段**线上零消费**——app 侧 `guard.ts` 连它们的形状都不校验，用户看到的那句话实际来自 `degradedReason`。C1 清账卡把它们删了。过程中踩出四条硬规则：

1. **零消费字段有三种命运，必须先分类再动手**：
   - **该删**：同义反复型（`reason` 的代码值 vs 已能完整表达的 `degradedReason`）。删掉是净收益。
   - **该留（且必须写明用途）**：契约自证型（`before`/`after` —— core 侧靠 `rebuild(chunks) === after` 证明 `chunks` 不丢字节，删了 `chunks` 就是孤证）。
   - **该用**：护栏型（`revision` —— 过期 diff 的唯一判据）。删掉等于把未来唯一的防线扔掉；正确动作是排期让消费方真的用它，而不是删。
   > 判据一句话：**"删了它，还有别的东西能证明同一件事吗？"** 能 → 删；不能 → 留下的必须写清"线上为什么有它"，且**不许美化**（`revision` 如实写"当前 app 尚未使用"）。

2. **注释也是代码的一部分**：删掉字段后，任何"前端会拿它做什么"的注释都成了替死人作证。C1 里 `annotation-basis.ts:60-66` 还写着"前端按 `originNodeId` 标这条批注原本属于哪块"——代码删干净了，注释还在描述一个不存在的消费者。**删字段的卡片必须把注释一起审计。**

3. **结构性恒真断言比没有断言更坏**：`focus` op 从 `Host` 移除后，`boot.test.ts` 的 `expect(ops()).not.toContain("focus")` 在结构上不可能失败，却让账本记着一笔"这里验过了"。删它之前必须证明**原意图已由别的断言承接**（测试员的办法：临时删 `boot.ts:273` 的副作用 → 用例变红 → 还原后 sha256 一致）。

4. **删掉门禁红灯时，只许收窄表面，不许放水**：C1 的 4 条 `knip` 红灯没有一条靠 `knipignore` 消掉——`spanOf`/`HtmlSpan` 是"门面重导出没人用"（删门面那两行），`ZERO_SPAN` 是"同一常量抄了三份"（归一成一份真值源，于是它有了真实消费者），`BlockBasis` 是"只在本模块用"（取消 `export`）。**能靠合并真值源解决的，绝不靠豁免。**

> 记账：`L-06`（`revision` 待用）/`L-07`（`before`/`after` 已裁定保留）/`L-08`（wire 无键集锁 → 零消费字段只能靠人审；下卡加 `Object.keys(body)` 键集锁或 zod 解析，把这类回归从人审变机审）。

### 11.12 交付报告的"绿"必须与 `pnpm verify` 同一集合（M3.1，2026-11-14）

**事故**：M3.1 写者报"typecheck / eslint / knip / depcruise 全绿"，我跑 `pnpm verify` **第一道就红**——`format:check` 三处未格式化。写者没撒谎，它报的"轻量四联"里**没有** `format:check`，而 `pnpm verify` 是九道。

**规则**：
1. 角色的"轻量门"= `pnpm verify` 的**真子集**，且必须显式列出跑过哪几道。派卡时协调者要在卡里写死这份清单，不许让角色自己猜。
2. **`format:check` 属于"改一个空行就能过"的门，必须放在四联里**——它成本最低、最常漏，而漏了它整链是 100% 红的。
3. 交付由**协调者**跑唯一一次全量 `pnpm verify`；角色跑定向用例 + 轻量门。角色若被要求跑全量，必须先确认没有别的 vitest 在跑（§11.10）。
4. **提交归属**：协调者 `git add -A` 会把工作区的中间产物（tsc emit 残留、临时脚本）一起扫进提交。M3.1 期间我这条命令把一个 docs 提交里塞进了 113 个 `.js` + 109 个 `.js.map` + 30 个源文件。**收口提交一律按路径显式 add，禁用 `git add -A`**；`.gitignore` 已补 `packages/*/src/**/*.js`、`*.js.map`、`*.d.ts.map`（**不忽略 `.d.ts`**——`ambient.d.ts` 是手写的，忽略它会把它藏起来）。

### 11.13 写者的"门禁全绿"永远是自述，不是证据（M3.2 F1，2026-11-15）

**事故**：F1 交付报告里写「`pnpm typecheck` / `pnpm knip` / `pnpm depcruise` / `pnpm format:check` / `eslint` 全绿」。我复跑，`typecheck`/`lint`/`depcruise`/`format:check` 四项确实绿，但：

Unused dependencies (1)
typebox  packages/pi-extension/package.json:11:6
[ELIFECYCLE] Command failed with exit code 1.
```

差异来源不是撒谎，而是**时序**：写者跑 knip 时 `package.json` 里还没有 `typebox` 依赖（F1 还没写 `Type.Object` 的用法，它先把依赖写上了）。门禁是快照，自述是记忆。

**规则**：

2. 反之，写者**必须**贴原始输出（命令 + stdout），只写"全绿"两字的报告直接退回——没有输出的绿无法被区分于"跑错命令的绿"。
3. 新依赖引入的批次，`knip` 要在**依赖与用法同一批**里落地；只加依赖不加用法必然红（本条的典型形态）。

### 11.14 用例名不等于断言：第二次"假证人"（M3.2 F1，2026-11-15）

**事故**：`packages/pi-extension/tests/sse-frames.test.ts` 有一条名叫"多字节 UTF-8 跨 chunk"的用例，刀口实际切在 `文` 与 `档` **两个字符之间**——证明的是"data 行没断"，不是"字被切成两半"。同一文件 `:64` 那条"CRLF 从中间分开"用的帧**根本没有 `id:`**，所以对"`id` 跨拆分存活"零分辨力；变异 `cutLine 不再等块尾孤立 \r` 因此 **35 例全绿**，而真实后果是 `id` 丢失 → `Last-Event-ID` 在真断线时静默回放整环。

**这是同一课第二次**（第一次是 M3.1.1 的哨兵臂：`toBe` 断言在没有哨兵时对来源完全盲）。差别在于：哨兵课是"断言没有分辨力"，这一课是"**断言有分辨力，但分辨的是别的变量**"——更难被发现，因为用例名字自证清白。

**规则**：
1. 用例名里出现的每个名词（"多字节"/"id"/"跨 chunk"）都必须在断言里有一个**只对它成立**的验证；名字里有几个变量，断言里就要有几条独立证据。
2. 变异测完以后要问一句反向问题：**"我删掉实现里的哪一行会让这条用例红？"** 答不出来的用例就是假证人。
3. 关键断言用逐字全等（`toBe`/`toEqual`），不用 `toContain`——`toContain` 只能证"包含"，不能证"仅此"。

### 11.15 只读审计员的报告必须"回传即落盘"（M3.2 G2-R1，2026-11-15）

**事故**：G2-R1 的审计员载体是 `reviewer`（只读，不能写文件），我按协议让报告"正文回传"，**当场没有落盘**。到 G2-R2 时审计员用 `find .workflow -name '*M3.2*'` 找不到 `M3.2-G2R1-audit.md`，无法做去重，只能靠卡 §7 的记录猜，并据此在不确定项里写了"最可能重复的两条请协调者覆盖"。原文已随上下文压缩丢失，最后只能按摘要重建一个索引文件。

**规则**：
1. **只读角色的报告，回传后立刻 `cp`/写盘**——不要等"这一轮结束再整理"。回传内容一进上下文就可能被压缩，而压缩是有损的。
2. 报告文件名统一 `M<卡号>-G<轮>-<角色>-<批次>.<ext>`，落盘后在同一条消息里 `ls` 一次，确认文件非空。
3. 派单给只读角色时，**不要让它"写报告文件"**（它写不了，会白烧一轮），要写"**正文返回，我来落盘**"。

### 11.16 变异测试的复原保障：未入库文件不能 `git checkout`

M3.2 的收尾轮出现一次：`packages/pi-extension/` 是**新目录、尚未 `git add`**，测试员做完变异想复原时 `git checkout -- <file>` 直接失效（untracked 文件不在索引里，命令静默无效），那次是靠 `shasum -a 256` 基线 + `diff -q` 逐文件校验才确认 15 个文件 0 不一致。

**规则（变异测试前必做）**：
1. 先确认目标文件**已入库**（`git ls-files --error-unmatch <path>`）；已入库才可用 `git checkout --` 复原。
2. 未入库：跑变异**前**存 `shasum -a 256 <files> > .workflow/tmp/baseline.sha256`，每次复原后 `shasum -a 256 -c` + `diff -q`，**并把校验输出贴进报告**。
3. 无论哪种方式，复原后都要**再跑一遍全绿**——只看 `diff -q` 不算，因为变异可能改的是格式化后的等价文本。
4. 报告里写清用的是哪种保障，不许只写"已复原"。

### 11.17 交付消息的字数上限

同一轮的三个角色都出现了报告膨胀：写者 25 → 49 行，测试员 20 → 两节各 30 行，审计员 220 行上限用满。**报告的价值在「判词 + 可复跑证据」，不在过程叙事。**

**规则**：交付消息 ≤ **25 行**，只允许四类内容——① 判词（一行）；② 每条变异/攻击的「结果 + 点名用例」（一行一条）；③ 我要求的定向输出尾部；④ 新发现的缺口（一行一条 + 指向报告节号）。**过程叙事、走过的弯路、"我又想了想"一律写进报告文件，不进消息。** 协调者要的是能不能结卡，不是复盘。

### 11.18 注释宣称的保证必须由代码兑现（M3.4，2026-11-16）

**事故**：`packages/core/src/ops/revert-op.ts:2` 写着"复用 patch 的同一条快照链"、"patch / style / 批注共用同一条链"。立卡时我把这句当事实写进了 AC-3（"patch → 换样式 → undo 只回退样式"）。写者实现时撞红，回头 `grep -rn "snapshot" packages/core/src/style/*.ts` → **零命中**：`applyFile` 从不写快照，所以一次 undo 会**把正文和样式一起回退**。注释撒了谎，而它撒的谎被写进了验收标准。

这是 `L-13` 判据（同一事实只拼写一处）的第十例，也是最贵的一例：**注释是契约的一部分**，不是备忘。一句"共用同一条链"读起来像事实陈述，实际是作者的期望。

**规则**：
1. 任何"复用/共用/同一条 X"的注释，都必须能用一个 `grep` 证伪或证真。写不出那条命令的注释，就改成陈述**本文件做了什么**，不描述别的文件。
2. 立卡时从注释里抄来的"事实"，必须先在代码里核一遍再写进 AC——注释与代码不一致时，**代码赢**，且这条不一致本身要登记成缺陷（`L-32`），不能只在卡里改口径了事。
3. 改口径还要留**防线**：`L-32` 修完之前，`docs/05` 的使用建议必须警示用户可见后果（"换样式后 undo 会连正文一起退"）。**反直觉的语义不许只存在于测试里**，因为测试是给机器看的，使用建议才是给人的。
4. 反直觉语义是**差分测试的富矿**：两条写入路径（MCP / HTTP）在同一个怪场景下必须同样怪。这比"各自都符合规格"强，因为它能抓到"其中一条偷偷换成了底层原语"。

### 11.19 修一处不实陈述时，先 grep 它的全文找副本（M3.4，2026-11-16）

**事故**：`docs/05-feature-cards.md:182` 与 `docs/02-architecture-and-roadmap.md:193` 各有一句“校验**目标文件**哈希未被外部改动”，而 `packages/core/src/io/undo.ts` 实际只校验**快照自身**的哈希（`sha256.startsWith(latest.hash)`）。写者按审计意见修好了 `docs/05`，`docs/02` 的副本仍是旧的；直到协调者回头 `grep -n "hr_undo" docs/02` 才发现。

**为什么不是个案**：同一项目的同一事实，通常在**架构文档的原语表、功能卡的使用说明、代码注释、`SKILL.md`** 四处各有独立拼写（`L-13` 的第十一例）。修一处等于把“两份错”变成“一对矛盾”，比不改更糟——后来人不知道该信哪一份。

**规则**：
1. 修任何关于**行为**的不实陈述前，先用该陈述里的关键名词 `grep -rn` 全仓（`docs/`、`skills/`、`packages/*/src`、`README.md`），列出所有拼写副本，一次全改。
2. 行为类事实的**唯一权威**是代码；文档之间互为副本，谁都不是权威。所以改完要用一条命令回证（`sed -n '<line>p'`）。
3. 反向也成立：**新增**行为说明时，只在**一个**地方写清事实，别处只写“见 `docs/05` 的 X 节”——副本越多，漂移越快。

### 11.20 路线图不是事实：立卡前先证"卡里的外部依赖真实存在"（M3.3，2026-11-16）

**事故**：`docs/02:245-251` 的 M3.3 要做一个 DSH(Cordis) 插件。立卡前我派了一路只读调研去证伪，结论是**半真半假**——生态真实存在，但三处细节是错的：

| 路线图写的 | 真实 |
| :--- | :--- |
| `dsh plugin add @hreader/dsh-bundle` | `--profile` 是 requiredOption，漏了就 usage 报错 |
| 插件入口 = `cordis.patch.yml` | 两份都要：`package.json` 的 `dsh.bundle.patch` + 该 yaml |
| "Prompt Hook / Interceptor" | 该概念**不存在**；真机制是 `ctx.systemPrompt.section()` + `system-prompt/assemble` waterfall |

另有两处更隐蔽的：`dsh@1.0.1` 是 2016 年的 JS shell（撞名）、`@deepseek/harness` 404，真实组织是 `@deepseek-ai/*`；`ctx.emit` 的类型合并必须写 `declare module '@deepseek-ai/cordis'` 而不是 `'cordis'`（写错**不报错**，只是校验静默失效）。

**这是 §11.18 的推广**：注释不是备忘而是契约，那么**路线图不是事实而只是提案**。若按错字段名做完一卡，会在真宿主上一次性崩掉，而在此之前 CI 全绿。

**规则**：立卡前，凡是卡里引用**本仓之外**的东西（包名、版本、入口字段名、API 名、CLI 用法），必须有一条可复跑的命令证明它的存在与形状：`npm view <pkg> version license`、`npm pack` 后读 `*.d.ts`、`grep` 官方模板。拿不到就写"拿不到，因为……"，然后把该条降级为"待验证"放进 §3 不在范围，不许当事实写进 AC。

**补充（F1 阶段的反向更正，2026-11-16）**：卡里初稿写的 `order` 带位是 `-100` identity / `0` persona / `100-199` tool guidance——**这是更早版本的真值**，`@deepseek-ai/dsh-system-prompt@0.2.2-rc.1` 实际是 `HARNESS_IDENTITY: -1000` / `DEPLOYMENT_PERSONA_PREFIX: 0` / `PLAN_POLICY: 500` / `TOOL_BASH: 1000` 起为工具指引（`lib/types/index.d.ts:123-152`）。写者按真值取 `100` 并给出理由，反过来纠正了我的卡。

**规则升级**：卡里凡引用**外部包内的常量/枚举/序号**，除了"证明它存在"，还要**贴出取值所在的行**（`sed -n '123,152p' <pkg>/lib/types/index.d.ts`）。"我记得是 100-199" 与 "路线图这么写的" 是同一类错误，只是一个记在自己脑子里、一个记在别人的文档里。

**副产物**：这一卡还顺带证明了两件事——(a) 风格规约的**内容**半边早就在了（`hr style --tone` 与 MCP `use-hreader-style` 都走 `compileTone`），所以"缺这个能力"的判断也要先 grep；(c) 面板要求 React + `window.__ModuleLoader__.load`，与 `docs/02:255`「无框架阅读器」直接冲突，被移出本卡。

### 11.23 「防御性相等分支」自己会变成死代码（M4.1 F1，2026-11-16）

**事故**：审计员提了一条 P2——`packages/core/src/style/extract/stats.ts` 的排序比较器在同键时回 `1`，违反比较器的自反契约。写者照办，加了一行 `if (left[0] === right[0]) return 0;`。这一行**永远不可达**：被排序的条目来自 `Map`，同一个 bigram 不可能有两个条目，而 `sort` 的比较器只拿两个不同元素。

更难看的部分：写者只跑了七个定向测试文件，全部 `Tests N passed`，于是在交付里写"全绿"；我跑全量 `pnpm verify` 第一次就红：

```
 stats.ts  |  100 | 96.87 | 100 | 100 | 78
ERROR: Coverage for branches (96.87%) does not meet global threshold (100%) for packages/core/src/style/extract/stats.ts
```

**规则**：
1. **"修一条契约"不等于"加一个 `if`"**。当你想加的分支是为了满足"理论上可能"的输入时，先问：这个输入能由真实数据构造出来吗？不能就把它变成**内部符号 + 直接单测**（`@internal` 导出，先例 `packages/core/src/style/spec.ts` 的 `syntaxErrorOf`），让覆盖率看得见它被覆盖。
2. **定向测试全绿 ≠ 全量绿**：`verify` 里带覆盖率门槛（perFile 100%），而定向 `vitest run <file>` 不会跑门槛判定。写者交付时**只能声称"定向 N 例通过"**，"全绿"三个字留给跑过 `pnpm verify` 的人（§11.13 的补强：本轮有人不是编造，而是**混淆了两种绿的语义**）。
3. 审计员提的 P2 也适用于自己：审计员说"同键应回 0"是对的，但**没说清怎么测**；执行者照做时若不问"谁能触发它"，就会把契约修成死代码。派单里凡涉及"补一条分支"，同时写明"这条分支由什么输入/单测触发"。

### 11.24 接缝的方向由下游消费者的真实输入决定，不由任务书的直觉决定（M4.1 F3，2026-11-16）

3. 裁定要给出"为什么"，因为写者会用同一条理由去处理下一处类似冲突（本轮它就自己推出了 `styleYamlOf` 不能外泄、`parseStyleText` 必须回读）。

### 11.25 花钱的调用必须排在所有确定性校验之后（M4.1 F3，2026-11-16）

**事故**：`--out` 的 `file_exists` 守卫原本排在 LLM 调用**之后**。测试员用"已存在目标 + 假 fetch 计数"实测：`fetchCalls === 1` 才报"目标已存在"——用户为一次注定失败的运行付了钱。同一轮还发现 `--base-url` 的**地址合法性**没校验，非法地址要等 Node fetch 抛 TypeError，被包成 `llm_failure`(exit 3) 并配一句"网络抖动可重跑一次"的误导文案。

**规则**：
1. 一条命令里若有"外部计费调用"，**把一切不需要网络的失败判定全部前置**（目标已存在 / 父目录缺失 / 路径越界 / 参数非法 / 金额上限）。用例必须断言 `fetchCalls === 0`，只断言 exit code 不够——exit code 在前置后置两种实现下都会是对的。
2. **参数校验的语义边界要写死在纯函数里**（本轮 `normalizeBaseUrl`：trimming + 去尾斜杠 + `URL.canParse` + 协议白名单），而不是依赖运行时框架的报错形态（Node fetch 不接受相对 URL 是**实现细节**，换 runtime 就变）。
3. 这个教训与 §11.23 是同一条根：**"理论上不会发生"的分支**（相对 URL、非法协议）一旦落在真实用户的输入面上就要有断言；反之纯内部不可达的分支就别加。

### 11.26 「端到端测试」退化成了冒烟测试（M4.1 F4，2026-11-17）

**现象**：`packages/cli/tests/style-extract-e2e.test.ts` 通过了真 `run(...)` → `loadStyle` → `compileTone` → `lintByStyle` 全链，看上去是本卡最硬的证据。测试员的变异表揭穿了它：`narrative_rules` 只写第一条（M2）**在 e2e 与全仓都不红**；`forbidden` 改成交集（M3）、语料不进 prompt（M4）、`--no-llm` 仍构造 LLM（M5）、LLM 路径写盘退回统计版（M9）——四个变异在 **e2e 上全部 SURVIVED**，只被别处的单元用例顺带杀掉。

**根因有三条，缺一条都不会出事**：
1. `fetch: () => Promise.resolve(new Response(RECORDED))` 无视请求体 → "发了什么"没有任何断言。
2. `--no-llm` 路径不数 `fetch` 次数 → "有没有偷偷花钱"没有任何断言。
3. 端到端只断言"能 load / 能 compile / 能命中"这类**可消费性**，不断言**内容的条数与取值** → 少写一半字段仍然"可消费"。

**规则**：
1. 端到端测试的必要条件不是"链路通"，而是**每条链路各有一个只有它写了才对得上的取值断言**（本轮：`narrativeRules` 的条数、`examples` 的组数、只在 LLM 侧出现的那个 `forbidden` 词、`persona` 等于录制值）。
2. 凡注入桩（`fetch`/时钟/随机）的端到端用例，**桩必须能回答"我被调了几次、我收到了什么"**；否则桩本身就是假绿的遮罩。
3. 写者在交付前自查一句：**"把这条链路的任意一环换成空实现，我的测试有几条会红？"** 数不出来就是冒烟。

### 11.29 跨文件"同口径"不变量，必须一维一条用例（M4.1，2026-11-17）

**事故**：`packages/core/src/style/words.ts:34` 的 `foldWord` 做三件事——NFKC、小写、剥零宽——用来保证"词表里的禁词"和"正文里的词"是同一口径。`spec.ts` 去重时也调它。测试只钉了 NFC 那一维（`spec-forbidden-dedupe.test.ts` 的 `["école", "e\u0301cole"]`）。

终轮变异把这件事暴露得很干净：把 `foldWord` 换成**只做 NFC** → 4 条用例全绿；把去重键换成 `word.toLowerCase()` → 也全绿。也就是说 NFKC / 大小写 / 零宽三维任意漂移，测试完全看不见。漂的后果不是"少报"，是**同一禁词的两种写法在 `forbidden` 里各报一条 hit**（`"ＡＢＣ"` 与 `"abc"`）。

**规矩**：一个"口径"函数有 k 个维度，就有 k 条用例，每条**只让其中一维起作用**的输入，并断言**输出值**（不是长度）。此处四维各一条：全角/半角（NFKC）、大小写、零宽、组合重音（NFC）。

### 11.30 判定可以 canonical，展示必须是用户输入（M4.1，2026-11-17）

**事故**：`--out` 的"不在风格发现路径里"提示，为了判定正确做了 realpath，然后把**同一个 canonical 串**既用于判定又用于打印。用户敲 `--out styles/x.yaml`，提示里打的是 `/private/var/.../styles/x.yaml`——提示在说一件用户没输入过的事，macOS 上还带上 `/private` 前缀。

**规矩**：canonicalize 只进判定路径；打印一律用 `intent`（用户输入的原样，必要时按 `io.cwd` 相对化）。两件事分开做，中间那层用 `displayedOutOf(intent.out, io.cwd)` 这样的纯函数，别让判定函数顺手返回值给人看。

### 11.31 真实文件系统里的软链，mock 复现不出来（M4.1，2026-11-17）

**规矩**：凡涉及"两个绝对路径是否同一"的判定，用例必须用**真的** `ln -s`（`symlinkSync`）+ 真的临时根，并保留一条"把实现退回 `resolve()` 版就红"的变异自证。同一原则见 §11.13（门禁只信自己跑的那次）。

### 11.32 子代理载体有三条硬约束：看门狗 30 分钟、代理由内置列表、`resume` 续接（M4.3 F1，2026-11-17）

### 11.34 写者自报"全量 verify 绿"必须由协调者复跑；守卫顺序是契约（M4.3 R4→R6，2026-11-17）

**事故**：R4 收尾时写者报 `pnpm verify EXIT=0`，我照例复跑，实得 `2 failed | 2668 passed`。根因不是"测试少"，而是**守卫顺序**：`exportPrint.ts` 把「目标已存在（`file_exists`/exit 1）」判在「越界（`path_outside_workspace`/exit 3）」之前，于是 `--out ../escape.html` 先落到 exit 1，**还真的把 11243 字节产物写到了 workspace 外面**（`$TMPDIR/escape.html`）。这个脏文件又让一条毫不相干的旧用例（`cli-exit-codes.test.ts`「should exit 3 for ../x.html」）变红——因为两条用例都把落点取成 `$TMPDIR` 下的同名文件。修完后测试员又验出第三个缝隙：把 `isInside` 换成 `path.startsWith(workspace)` 全绿存活（共享前缀兄弟目录 `<base>/w` vs `<base>/w-evil/x.html` 正是 `startsWith` 的经典漏点）。

**规矩**：
1. **写者自报的全量绿只当线索**。收口前由协调者在仓库根亲跑 `pnpm verify`（§10.12 的延伸：不采信"我跑过了"）；写者被要求报 `Test Files`/`Tests`/`All files` 三行原始数字，而不是 `EXIT=0` 四个字符。
2. **守卫顺序本身就是契约**：前置守卫（越界/权限/stdout 冲突）必须排在状态守卫（`file_exists`）之前——退出码由**第一个**触发的守卫决定，顺序错了就把 3 折成 1，配再多的用例也测不出来（除非用例构造出"外面已存在"的形状）。
3. **用例只许在自己的临时目录内落盘**，落点用**唯一名**（pid/时间戳/`mkdtemp`）+ `finally rmSync`，并且断言"没落盘"（`readFileSync` 抛 `ENOENT`）而不只断退出码。跨用例共享落点是假绿的第二来源：一个用例写脏了，红的是另一个用例。
4. **路径判定用 core `isInside`（归一 + realpath 两段），不用 `startsWith`**；`startsWith` 必须有一条"共享前缀兄弟目录"用例钉死（`<base>/w` workspace / `<base>/w-evil/x.html` 目标，且目标**已存在**才杀得死变异）。
5. `$TMPDIR` 里 949 条长期泄漏（`hr-watch`/`hreader-undo-home`/`hr-docid`/`hreader-style-*` 等，来自 watch/docid/undo/style/dist 套件）是**既有技术债**，与 M4.3 无关，登记在卡 §14 未修项里，别在里程碑收口时顺手改。

### 11.35 自己定的"保守上限"必须有一条真机「能过」的反证（M4.4 R6→R7，2026-11-17）

**事故**：`PIXEL_EDGE_LIMIT = 16384` 是我在卡里拍的"单边保守闸"，四条 AC 用它判"拒绝"全绿；但测试员拿真 Chrome 出了一张 `1200×76663` 的图——**上限本身是假的**，落在区间内的合法请求（默认档 9 页 A4 = `2400×17634`）被静默拒掉，而所有断言都在测"拒绝得对不对"。

**规矩**：
1. 任何**数值上限**进卡时，必须同时给出"上限之上的真机证据"或"为什么拿不到证据"。只写"保守取 X"等于把锅甩给未来。
2. 拒绝类用例（`invalid_input`）不能证明上限**合理**，只能证明代码按数字执行；**必须有正向用例证明"该放行的放行了"**，且该正向值要贴近真实负载（本例：默认档 17634）。
3. 上限调到真值后，注释要说明**保守余量**从哪来（"真机 76663 也能出，此处留余量"），不许写"这是光栅层天花板"——PNG 规范上限是 2^31−1，写一个自己也不验的物理事实比不写更坏。

### 11.36 用「用户没说的默认值」预检，就是在用默认值拒绝用户（M4.4 R6→R7，2026-11-17）

**事故**：面积闸预检无条件用 `maxHeight` 的**默认值** 20000 算最坏面积，于是 `--width 4096 --scale 3`（宽度合法、内容仅 5110 CSS px）被判 `4096×3×20000×3 = 737M > 2.5e8` 拒掉。用户在请求里**没提** max-height，却被默认值杀死。

**规矩**：
1. 预检只能拿**用户显式给出**的值做最坏情况估算；默认值只能用于"实际渲染时的截断"，不能用于"进门时的拒绝"。
2. 表达"显式"要用**裸布尔**（`args-png.ts` 的 `maxHeightExplicit: raw.values.has("--max-height")`），**不许**用 `undefined` 哨兵或"等于默认值就当没传"——前者违反 D7，后者在用户恰好传了默认值时误判。
3. 量到真实值之后的那道闸（本例 `cdp.ts:231-236` 的 `assertPixelFrameOf`）**永远要查**，与显式与否无关；两道闸的分工写进注释，别指望读代码的人自己推。

### 11.37 只测拒绝分支的闸，等于没测（M4.4 R7→R8，2026-11-17）

**事故**：R7 补了两个闸的正向/拒绝用例，审计员仍能指出两处全绿存活的变异：「凡显式 `--max-height` 一律拒」和「把 `contentHeight > 1000` 写成 `>= 1000`」——因为 `maxHeightExplicit: true` **只出现在拒绝用例里**，而 `contentHeight === 1000` 这条边界根本没用例。

**规矩**：一个分支/闸要配**三类**用例，缺一条就不算测过：
1. **拒绝**（`invalid_input`，钉住错码与 message 里的实际值/期望值）；
2. **放行**（同一条闸的合法输入必须过——上例 `1200×2 + maxHeight 20000 + explicit` → `96M < 2.5e8` 不抛）；
3. **恰好等于边界**（`=== 1000`、`=== 65535`、`== 2.5e8`）：把 `>` 写成 `>=` 必须变红。

### 11.38 视口地板会把短文档撑出白边；量高要能"复位再量"（M4.4 R7，2026-11-17）

**事故**：量高用固定 `MEASURE_HEIGHT = 1000` 落视口，而 `cssContentSize.height` 是 `max(内容高, 视口高)`——几百像素的短文档一律被量成 1000，长图上下各多一条白边。所有长文档用例（4661/16000/30000）都发现不了。

**规矩**：
1. 凡是"用测量结果反推真实值"的地方，都要问一句**测量下限会不会污染结果**。本例的下限就是视口高。
2. 修法是**复位再量**（`contentHeight <= MEASURE_HEIGHT` 时以 100px 视口重落一次再量），不是"减掉 1000"——后者在内容真的 1000px 时会把高度算成 0。
3. 边界必须有用例（本例 `=== 1000` 进复量分支、结果仍是 2000 设备像素），否则"复量分支永不触发"与"复量分支吃掉所有输入"两种坏法都能全绿存活。

### 11.39 「上游做不到」要先用一个探针否掉，再立卡（M4.5 立卡前，2026-11-17）

**事故**：M4.3 的路线图里写着「带目录书签的 PDF 在浏览器打印下**不可实现**（无 paged-media 计数器与 PDF outline 控制）」，据此把大纲拆成 M4.5 预备另写 PDF 增量更新（追加 `/Outlines` + `/Prev` xref，需要自写 PDF 对象解析）。立卡前花 10 分钟跑了一个探针：同一份打印稿只改一个参数 `generateDocumentOutline: true`，产物直接从 41545 → 43078 字节，Catalog 多出 `/Outlines 59 0 R`，根 `/Count 9`、标题含编号、层级成树、`/Dest [pageObj /XYZ …]` 页码全对。

**规矩**：
1. 路线图里任何「X 不可实现」的断言，**开卡前用一个最小探针复核**（本例 20 行：起 Chrome、`Page.printToPDF`、`strings` 看 trailer）。成本 10 分钟，收益是整张卡从「自写 PDF 解析器」缩到「一个参数 + 两个旗标」。
2. 探针结论必须带**可复述的数字**（字节数、`/Count` 值、`/Kids` 顺序），不许写「支持」。数字进卡 §1 之后，写者就不需要重跑侦察。
3. 探针顺带会暴露口径陷阱：本例发现 Chrome 收 **h1–h6 全部**（加一个 `h4` 条目 9→10），若按「只数 h1–h3」的直觉写断言，会得到一份永远红或永远绿的测试。

### 11.40 计数口径要数「产物生成器的输入」，不是「我以为的语义源」（M4.5 A1，2026-11-17）

**事故**：`--json.outline` 有三个候选口径——打印稿 HTML 里 `<h1..h6>` 元素数（A）、`buildOutline().nodes` 摊平数（B）、源 `<article>` 里的 heading 数（C）。B 会被 `OUTLINE_DEPTH_LIMIT = 4`（`packages/core/src/ops/outline/constants.ts:23`）与「缺 `data-hr-id` 就省略」（`walk.ts:130-133`）**悄悄缩小**，C 会把封面/页头的标题算进来，而两者都与 Chrome 实际看到的 DOM 不同。

**规矩**：
1. 「报告里的数」必须与「产物生成器真正吃的那份输入」同源。Chrome 吃的是**打印稿 DOM**，所以口径就是 `parseHtml(product.html).root` 上数元素——A。
2. 选口径时要问：**这个值在哪种输入下会与产物不一致**？本例答案是「`display: none` 的标题」——DOM 里有、书签里没有。这种已知不一致**必须写进注释与限制表**（`L-40`），不许留成「偶尔差 1」的谜。
3. 不许用正则数 HTML 标签（`/<h[1-6]\b/`）：注释里的 `<h1>`、属性里的字符串都会被数进来。用解析后的元素树。

### 11.41 手写字节夹具如果「顺着扫描器实现编」，扫描器的 bug 会一起通过（M4.5 R1，2026-11-17）

**事故**：`pdf-scan.ts` 用 `/Root`→`/Pages`→`/Kids` 递归算页序，实现是对的，但夹具 `pagesOf(n)` 只造 `Pages → Page` **扁平**树，且 `/Kids` 顺序恰好等于对象号升序。于是两个变异全绿：把递归改成「只摊一层」（MV-11）、把 kids 按对象号排序。

**规矩**：
1. 手写夹具要覆盖**实现的每一条分支**，尤其是「结构可能嵌套」和「顺序与编号不一致」这两类——它们正是「看起来对」的变异最爱藏的地方。本例补了 `CHAIN_PAGES`（四层 `Pages→Pages→Pages→Page`；三层不够，三层时「只摊一层」得到的仍是正确答案）与 `REVERSED_KIDS`（`/Kids [7 0 R 5 0 R]`）。
2. 补夹具的同时**当场把变异打进去验证它变红**，并把「N failed」贴进报告；只加夹具不验变异，等于给自己发合格证。
3. 夹具文件头要写明「这份夹具存在的唯一理由是钉哪个变异」，否则下一个人会当冗余删掉。

### 11.42 「跑过一遍」不等于「树里有这条断言」（M4.5 R1，2026-11-17）

**事故**：测试员用真 Chrome 手工验完了 AC-5/AC-6（标题保真、`/Dest` 页序、两次渲染一致），报告里有证据，但**树里没有对应的 e2e 用例**。审计员因此把「空白正常化退化成 `trim()`」（MV-16）标为存活变异——报告绿、树里空。

**规矩**：
1. 真机证据分两种，**必须分开写**：① 一次性探针（用来定事实，写进卡 §1 就作废）；② 提交进树的 e2e（用来防回归）。AC 里凡是「以后可能被改坏」的断言，必须落到 ②。
2. e2e 的 oracle 不许退化成「看起来相等」：本例标题比较必须两边都过 `normalizeWhitespace`（`packages/core/src/html/text.ts:45`），否则把归一改成 `trim()` 仍然全绿。

### 11.43 覆盖率 100% 不等于变异充分性：洞在「条件根本没被评估」（M4.5.1 G3'，2026-11-18）

**事故**：`bookmarks.ts` 的 `trailerOf` 里有一道「只认 `startxref` 之前的 `trailer`」过滤，分支覆盖率 100%。把整个过滤删掉 → **2937 例全绿**。原因不是等价变异：那条看似对口的用例钉的是「`% trailer << … >>` 写在注释里不算」，而注释字节压根不会变成 `PdfTrailer`——**它从未经过那道过滤**。

**规矩**：
1. 看到一个条件分支，要问用例是否真的**经过**它：经过的方式必须是让条件**为假**，而不是让条件**没被评估**。后者是覆盖率数据看不到的盲区。
2. 每张卡收尾必须跑一轮变异验证（改坏 → 跑全量 → 记录哪条用例红），且每条变异要能回答「为什么是这条红」。**出现全绿变异就是洞**，不许以「等价变异」放行——先造反例证明它不等价（本例：真 trailer 之后再写一个非注释 `trailer << /Size 99 /Root 99 0 R >>`，原实现得 1 条、变异后抛「找不到 Catalog 对象 99」）。
3. 百分比不是证据。卡里写「四维 100%」只能证明行被走过，不能证明断言能抓住改变。

### 11.44 死分支不许用 ignore 养；只在真机路径成立的断言等于没有断言（M4.5.1 R3，2026-11-18）

**事故 A（想开先例）**：给环检测再加一道步数上限做冗余守卫，它与 perFile 四维 100% 门禁互斥——合法遍历每步占一个对象号 ⇒ `steps ≤ 对象总数`，而重复必定在 `seen` 处更早被逮住，所以那道 `throw` 按构造不可达。于是想用 `/* v8 ignore */` 让它过关。

**事故 B（只在真机成立）**：删掉 `stream`→`endstream` 跳过，只有真机 e2e 变红，`HREADER_SKIP_CHROME=1` 下 2932 passed 全绿——无 Chrome 的 CI 上这条防线不存在。

**规矩**：
1. 全仓禁 `v8 ignore` / `c8 ignore` / `istanbul ignore`（`packages/mcp-server/dist/*` 里命中的是打包依赖，不算我们的源码）。第一条例外是所有门禁瓦解的起点。
2. 冗余守卫的取舍写成**「为什么不做」的正向注释**（本例：鸽笼约束 ⇒ 环由 `seen` 负责 ⇒ 第二道 throw 是死分支，只能靠豁免养着，得不偿失），不是 `TODO`。宁少一道守卫，不开覆盖率先例。

4. 删掉「防挂死」守（如环检测）后回归形态是**整轮挂死**而不是红，这是被接受的残余风险，靠 CI 作业级超时兜底——这个取舍要写进卡，不要用「加步数上限」去换覆盖率。

### 11.45 「进程没了」不是「进程自己退的」：验收要能区分退出方式（M4.2 G2″，2026-11-17）

**缺陷**：`hr serve --exit-with-parent` 的看门狗定时器永不回收（`clearInterval` 只写在 parentGone 分支，stop 路径不碰它，且没 `.unref()`）。带旗标时 `kill -TERM` 后 daemon **3s 仍活**、`daemon.json` 却已删——**服务关了、进程还在**；不带旗标同一脚本 200ms 自退。

**为什么连过两轮验收**：桌面壳的 `Drop` 是 `kill -TERM` → 等 2s → `SIGKILL`，所以真机案拿到的 `daemon_alive=no` 是**被 SIGKILL**，不是自己退。整整两轮，验收都在用「进程死没死」这个指标，而它对这个缺陷不敏感。

**规矩**：
1. 凡验收「进程应自己退出」，**必须同时拿到退出方式**：`wait` 的退出状态、`kill -0` 轮询到消失的时刻、或 `strace`/日志里的 signal 记录。只报 `daemon_alive=no` 视为**证据不足**。
2. 宿主侧兜底（SIGKILL / 超时强杀）会**掩盖**被宿主的子进程的退出缺陷。凡"父进程会收尸"的场景，测试必须**绕开收尸**单独验子进程（本卡：不开壳，直接 `kill -TERM` daemon）。
3. 反向判据更好用：**同一脚本换开关跑两次**（带旗标 vs 不带旗标）。缺陷只在一条路径上时，对照实验比单点断言更快暴露它——本卡就是这样一眼看出来的。
4. 泄漏型缺陷（定时器/句柄/listener）没有"错值"，只有"该退不退"。给它配的用例要用 fake timers 断**资源归零**（`vi.getTimerCount() === 0`），不要断某个布尔值。

### 11.46 变异前先设沙箱环境，破窗顺序反了就是事故（M4.2 R2，2026-11-17）

**事故**：跑「`io.home` 被忽略」变异时先改了代码、后设 `HOME` 沙箱。变异体落回真实 `homedir()`，那条用例真的执行了洞——**覆盖并删掉了用户的 `~/.hreader/daemon.json`**。token 不可重建；所幸那是陈旧记录（无活 daemon），"文件不存在"恰是正确终态，故未补偿。

**规矩**：
1. 变异脚本的第一行是**环境隔离**，第二行才是改代码。顺序不可换。`HOME`、`TMPDIR`、`XDG_*`、端口、run 目录都要在变异前就位。
2. 任何会写真路径的用例，其守门断言必须**同时**证明它写的是注入路径（本例：断言 `<injected>/.hreader/daemon.json` 出现），否则"洞被执行"时测试反而是绿的。
3. 事故本身是**洞为真**的证据：能污染真实目录，说明该路径没有沙箱边界。修完把"必须先设沙箱"写进脚本头注释，别只写进报告。

### 11.47 新加的门禁必须先用反例自证：`find -exec` 的两种写法都是假绿（M4.2 R3/R4，2026-11-17）

**事故**：给 `scripts/gui/**/*.sh` 加语法门禁，写成 `find scripts/gui -name '*.sh' -exec bash -n {} +`。5 个脚本只有 **1 个**真被解析——`bash -n f1 f2 f3` 里 `bash` 只把**第一个 operand** 当脚本，其余是位置参数。

find_semicolon_exit=0                            ← 但门禁仍绿
```
因为 `find` 的退出码只反映**遍历错误**，`-exec` 的命令失败只是"谓词为假"，不影响 exit。**报错 ≠ 失败**，这条比第一种更阴。

**最终形态**：`find … -print0 | xargs -0 -n1 bash -n`（每文件一次调用 + 失败折成非 0）。

**规矩**：
1. 新门禁落地的**第一件事**是造一个必须被它抓住的反例，跑一遍看它真红；跑不出红就说明门禁是装饰。本卡两轮都栽在"加完没做反例自检"。
2. 判据必须是**退出码**，不是"日志里有 error"。`find -exec`、`xargs` 无 `-0`、`grep -q` 在管道里被 `tail` 吃掉状态，都会让退出码失真。
3. 审稿人给的修法也要复核："建议 `\;`"来自审计员，同样是错的——**谁的建议都要过反例**。
4. 多文件循环的工具（`bash -n`、`node --check`、`python -m py_compile`、`tsc` 单文件）都要问一句"它接受几个 operand"。

### 11.48 `git status` 的 `??` 就是未入账的产出：整个桌面包在 git 外活了三张卡（M4.2 结卡，2026-11-18）

**事故**：M4.1（桌面壳）、M4.1.1（退出语义）都"结卡"过，M4.2 的一堆门禁也在跑 `cargo`——但
```
$ git ls-files packages/desktop | wc -l
0
$ git log --all --oneline -- packages/desktop
(空)
```
`.gitignore` 只忽略 `src-tauri/target/` 与 `gen/schemas/`，包本身**从来没被 `git add` 过**。克隆仓库看不到壳，而文档写着 M4 完成。原因：结卡提交用 `git commit -am`-式的"已跟踪改动"路径，**未跟踪目录永远不进去**，`git status` 里的 `??` 被当成噪声扫过去了。

**规矩**：
1. 结卡门禁多一条——`git status --porcelain | grep '^??'` 必须是**空**（或只剩本轮明确要新建、且即将 `git add` 的文件）。`??` 不是噪声，是"还没入账的产出"。
2. 提交前 `git ls-files <新目录> | wc -l` 必须与 `ls -R` 的文件数对得上：**新增整包/整目录时，`git add` 是显式动作**，不写就是没交。
3. 门禁跑绿 ≠ 产出在仓库里。`pnpm verify`、`desktop:check` 都在工作树里跑，**工作树有、git 里没有**依然全绿——这正是三张卡都没发现它的原因。

### 11.49 门禁不在 CI 里 = 门禁只在你的笔记本上（M4.2 R7，2026-11-18）

**事故**：`package.json:7` 的 `verify` 有八步，`.github/workflows/ci.yml` 的 `checks` job 只有六步——**`lint:sh` 与 `build` 不在 CI**。而我们为 `lint:sh` 连打三轮（§11.47 的两种假绿、空集、遍历失败），它却从来没在 CI 上跑过一行。"本地 `pnpm verify` 绿"被当成"CI 绿"用了整整两张卡。

**规矩**：
1. **`verify` 与 CI 的步骤表必须一一对应**。改 `verify` 的同一次提交里改 `ci.yml`；新增一步就在两个地方各加一行，并在 `ci.yml` 顶部留一行 `# 与 pnpm verify 的八步一一对应：少一步就是"本地绿、CI 不查"`。
2. 结卡证据里要贴的是**两条**：本地 `pnpm verify` 的退出码 + `ci.yml` 里对应步骤的 `grep` 结果（行号）。数字对不上就是漏一步。
3. 同一病灶的一般形式：**"这套判据在哪跑？"**每次加门禁都问一遍。答案若是"我手动跑过"，它就不是门禁，是笔记。

### 11.50 一棵树只能有一个写者（M4.2 R7/R8a 并行，2026-11-18）

**事故**：为省墙钟，我把 R7（`ci.yml`/`lib.rs`/`lib.sh`）与 R8a（`packages/cli/tests/units-run-home.test.ts`）同时派到一个工作树。文件不重叠，但**门禁重叠**：R7 首跑 `pnpm test:coverage` 撞上 R8a 写的 `coverage/.tmp`（`ENOENT`），`cargo test` 的 doctest 撞上并发编译（`E0463` can't find crate），两次首跑各红一次、复跑才绿。测试员 G4 同时也在同一棵树里跑 `verify`，它只能额外记一节"主树漂移"。

**规矩**：
1. **同一工作树同一时刻只允许一个写者**。要并行，就 `worktree: true` 或让其中一个只读（审计/测试可以并行，写作不行）。
2. 门禁是**进程级共享资源**（`coverage/.tmp`、`target/`、`node_modules/.vite`）。两个写者并行时，"我第一次红了但复跑绿"不是环境噪声，是**我自己造成的竞态**——出现这类报告先怀疑调度，别怀疑代码。
3. 派活前的默认检查：**谁在写、谁在读、门禁归谁**。三者有冲突就串行。

### 11.51 协调者自己验门禁时，也会用管道把退出码吞掉（M4.6 F1 收口，2026-11-18）

**事故**：撞 `check-ci-parity.mjs` 的第一个反例时我写的是
```bash
node scripts/check-ci-parity.mjs | tail -3; echo "EXIT=$?"
```
`$?` 取的是**管道最后一个命令**（`tail`）的状态 ⇒ 打印 `EXIT=0`，而脚本其实是 1。差一点就把"门禁能被弄红"写成"门禁没红"。同一类错误 §11.47 已经记过一次，那次是 `pnpm` 的 `sh -c` 没有 `pipefail`；这次是**我自己在 shell 里重犯**。

**规矩**：
1. 要退出码就**先重定向到文件再单独取**：`node x.mjs > /tmp/a.log 2>&1; echo "EXIT=$?"`。想在管道里取，用 `set -o pipefail` 或 `${PIPESTATUS[0]}`。
2. 反例证据必须写成**三件套**：命令、退出码、命中的那行输出（指名道姓，例如 `缺失（verify 有、ci 没有）：knip`）。只有退出码时，读者无法区分"红在正确的判据上"和"红在语法错"。
3. 撞完反例**必须 `cmp` 回原文件**（`cp bak` 不够，要 `cmp -s a b`），否则"我改回去了"只是记忆。

### 11.52 比对脚本只比「步骤在不在」，一行 YAML 就能让它永久绿（M4.6 审计 P1-1，2026-11-18）

**事故**：`scripts/check-ci-parity.mjs` 首版只读 `- run:` 行，比对 `verify` 与 `ci.yml` 的步骤**列表**。于是：
```yaml
      - run: pnpm knip
        continue-on-error: true     # 步骤级：脚本 → EXIT=0（本该红）
  checks:
    if: false                       # 作业级：脚本 → EXIT=0（本该红）
```
两道旁路都不用改脚本、不用改测试，**一行 YAML**。这是第四次"门禁在位但永不红"（前三：`find -exec +`、`\;`、空集），根因同一个：**我们只验证了形，没验证"它还能不能失败"**。

**规矩**：
1. 任何"门禁的元检查"都要回答两个问题：**在不在**（集合/顺序）+ **还能不能失败**（有没有被修饰成永不失败）。只答第一个是假绿。
2. 让步骤失去杀伤力的键是禁止项，命中即非 0 退出并指名键名与行号：步骤级 `continue-on-error` / `if` / `shell` / `working-directory` / `env`；作业级 `if:`（`needs` / `timeout-minutes` / `runs-on` 放行）。
3. 脚本头注释必须写**能力边界**：本脚本证明"两侧步骤同序同集且未被修饰成永不失败"，**不**证明步骤真被执行、不检查脚本内容。边界不写清，下一个人就会以为它证明得更多。
4. 真有"某步骤允许失败"的需求时，**改那段脚本的判据**（让它在该红的时候红），不要用 YAML 开关解锁门禁。

### 11.53 自证脚本和被告共用退出码，等于一起变哑（M4.6 终测 MV-7，2026-11-18）

**事故**：`check-ci-parity.mjs` 的内建 selftest 与它自己的判定走**同一个进程、同一个退出码**。把 `abort()` 里的 `process.exit(1)` 改成 `process.exit(0)`，6 个反例和被告**一起变绿**——但我上一轮让写者防的方向（"断言写恒真""多行静默跳过"）其实早被 selftest 抓死了，真正没设防的是这一条。写者判断只对一半，靠变异才看清。

**规矩**：
1. **期望值与判决必须不同源**：反例的期望退出码只写在父进程，判决由 `spawn` 出去的子进程给出（`node <self> --ci /tmp/x.yml …`）。两处都在同一个文件里也行，但**不能是同一条退出路径**（父进程用 `process.exitCode`，被告用 `process.exit`）。
2. 每个 selftest case 断言三件事：**专属期望串命中** + **其它 case 的期望串不出现**（防重言：任何一次 abort 都打印同一批标签，等于没断言）+ **期望退出码与实际一致**。
3. 自证脚本自己也要被打靶：把被测的失败出口改成成功（`exit(1)→exit(0)`），**整条命令必须变红**；变不红就说明自证和被告同源。这条要贴命令、退出码、命中行（§11.51 三件套）。
4. bash 侧同理：`lint-sh-selftest.sh` 末尾自调用一次已知坏命令，若"自己被人改成恒 0"，这次子调用就会返回 0 ⇒ 红。两行成本，防的是同一类。

### 11.54 把「超时」当判据，等于把 bug 和限速器混成一个信号（M4.7，2026-11-18 结卡）

**事故**：`L-43`（`sse-v4.test.ts > v4#1b` 全量并发下偶发 `Test timed out in 5000ms`）的根因不是服务端，是**测试夹具自己**：等帧靠一把 5000ms 的墙钟，超时即静默 resolve 已到的字节。于是「服务端没发帧」和「vitest 先到 5s」变成同一个红灯，诊断文本永远出不来。往里查还挖出三层假绿同源：

1. **grep 门禁冒充行为断言**：`clearTimeout` 只在 `verify` 里被 `grep` 守（AC-11），把它删掉整棵树仍全绿——门禁在位，行为无人证明。
2. **`it.fails` 靠超时冒充预期失败**：`wire-http.test.ts` 那条 KD-07 的 `it.fails` 之所以「通过」，是因为 `harness` 在 4000ms 静默 resolve 空串后断言失败——把「未实现」与「超时」混成一个信号；收紧窗口后它稳定红在 `4012ms`（**12ms 就是超时的指纹**）。
3. **恒真断言**：`expect(() => sse.close()).not.toThrow()`（`close()` 里只有 `shutdown("")` 与 `socket.destroy()`，不抛）与「从不下发帧场景下的 0 帧断言」，删掉被测行为照样绿。

顺带一个反转：KD-07 的退表理由**不是**「修好了」，而是「**前提过期**」——`http-io.ts` 的 `aborted ⇒ 408` 分支存在但线上抢不到响应（Node 内置 parser 先报 `HPE_INVALID_EOF_STATE`，默认写死裸 400；`grep clientError packages/core/src/server/` 零命中）。这条结论不靠日志顺序，靠两条**互斥事实**：若 408 赢，客户端必收到 `HttpFault` 的 JSON 体；实测只有空体 `HTTP/1.1 400 Bad Request`。

**规矩**：
1. **时间只能用来「比 vitest 早失败」，不能用来「判行为」**。夹具的等帧上限必须严格小于 vitest 预算（现为 `SSE_DEADLINE_MS = 3000 < 5000`），socket 兜底另设一个**远大于任何用例预算**的常数（`SOCKET_LIFE_MS = 60_000 > 30_000`），三个时钟都写死在注释里，且**超时必须抛错并自述**（已收几帧、订阅时刻、每帧偏移），不许静默 resolve。
2. **判据本身要被验证**。给「清埋」写断言时，别自报计数（`activeSocketTimers()` 的 +1/-1 与 `clearTimeout` 是否真执行无关，删掉 `clearTimeout` 仍 3→0）：改用 `vi.getTimerCount()` 的 delta，判据是「注释掉 `clearTimeout` ⇒ 红」，并 `toFake` 只 fake 两个定时器、`finally` 里 `useRealTimers()`。
3. **恒真断言一律删**，不许留着充数：一个删掉被测行为仍绿的断言，比没有断言更坏（后来人会以为这里被覆盖）。
4. **`it.fails` 不作为记账手段**：它天生把「未实现」与「超时/异常」混成一个信号。要么补真断言转正（本卡的做法：`400 + elapsed < 1000`，且**不绑 body 形状**，以免将来修对了反而红），要么退表并写清「缺陷不再成立」的证据。
5. **引用源码注释前先验它是否还对**：`wire-http.test.ts` 里那段「真 bug：Promise 永不落地」的注释让审计员判「已实现」、测试员复述「408 已实现」，**三个人都信了**。过期注释是文档级假绿，比测试级假绿更难发现。
6. **报告里引行号必漂**（同一处连错三次：`:252` 实为 `:254`、`:263` 实为 `:262-265`）：改引**符号名**，行号只作当时的近似值。
7. **退化变异要标「无鉴别力」**：本卡里「删 `chunksOf` 的 `aborted` 块」对本用例不敏感，写者一开始做成「一对变异」想凑红绿；正确做法是**明写不采用 + 理由**，不许留下假装跑过的变异记录。


### 11.55 测试代码的作者必须与业务代码的作者不同：同源闭环让 2974 例全绿也没有入口（M4.8 前置，2026-11-19 用户裁定）

**事件**：M4.7 结卡后让用户试用，一分钟内撞到两个坑——①`hr serve` 打印的 `serving … on http://127.0.0.1:8805/` 单独打开返回 `{"code":"unauthorized"}`（没带 token，也没教用户怎么拿 cookie）；②手写 HTML 直接进不了阅读器（`invalid_document`：`<article>` 缺 `data-hr-id`），而全仓没有"给文档注入 id"的入口——`injectNodeIds` 有 100% 覆盖，但**用户调用不到**。

**为什么套件没抓到**（这是本节的核心）：链条是 `实现 → 业务编写员写测试 → 测试员做变异`，三者共享同一套假设。
- 测试继承了实现的假设："文档自带 id"。手写稿路径整条不在视野里 ⇒ 覆盖率高而无入口。
- 变异体也**从实现推出**（改 `if (closed) return`、改 `< 1000`、改边界）。变异只能证明"用例能杀掉实现自身的变体"，**杀不出"这条路径根本不存在"**。
- 最典型的一条断言：`packages/cli/tests/units-serve.test.ts:65` 用 `/^serving .+ on http:\/\/127\.0\.0\.1:\d+\/ \(pid \d+\)\n$/u` 匹配打印文本——它在确认"实现有没有按我写的样子打印"，从没**照着这行字去访问一次**。`docs/03:64/136/176` 早就要求"用户视角黑盒实验"，被我自己派单时退化成"变异 ≥6 条 + 连跑 N 次"。

**用户裁定（2026-11-19，四角色）**：
1. 测试代码由**独立的测试编写员**写（§1.2b），业务编写员**不得碰 `tests/**`**（§1.2）。
2. 测试的出发点是**攻击功能**：从用户旅程、公开契约、失败模式反推，而不是跟随实现的分支结构。
3. 测试员从外部**双向攻击**：攻击实现，也攻击测试编写员写的用例（§1.4、§3.4）。

**规矩**：
1. **同作者不写测试**。业务编写员改了 `tests/**` 即越界，退回；反之测试编写员改 `src/**` 亦越界。两边的"停下来报告"通道见 §1.2 / §3.2b。
2. **每条用例必须能说出"实现怎么变坏它就红"**，说不出就是装饰，删掉（§1.2b 的判据自检）。
3. **首用路径是必测维度，不是加分项**（§4 新增 journey 行）：从空目录、只凭 `--help` 与文档走到产物。
4. **可发现性优先于字符串形状**：程序打印给用户的地址/命令，必须有测试**照它执行**；正则匹配打印格式记为弱断言（§4 第 4 条）。
5. **入口清点**：功能声明的入口（CLI 子命令 / HTTP 路由 / MCP 工具 / UI 交互）逐个确认有"从用户入口走到它"的用例；有入口无用例 = 假覆盖（§4 第 5 条）。
6. **测试员必答第二问**："有没有办法让这批用例全绿而功能是坏的？"（§3.4）——只答第一问（能不能引起 bug）不够，因为闭环内部永远自洽。
7. **归属随缺陷走**（§3.4/§6）：实现缺陷 → 业务编写员返工；用例缺陷（弱断言、缺失面、锁实现细节）→ 测试编写员返工；两者都不许"改测试让它绿"或"改用例迁就实现"。

## 十二、产品级巡回测试模式（Product Sweep，2026-11-19 起，用户裁定）

逐卡门禁（§三）用于**新增功能**。当项目已经"整体可运行"，改用本模式：以**完整产品**为被测对象，按轮次巡回，而不是按卡验收。

### 12.1 一轮 (Round) 的六步

```text
R<n> 开始
 ① 测试员（全新会话，上下文清空）先跑测试套件：verify / desktop:check / test:e2e / smoke:*
 ② 同一测试员以「真人用户」身份，从零把 <entrypoints 清单> 每一项跑一遍（只读 docs 与 --help）
 ③ 交一份缺陷台账 sweep-R<n>.md：B-01…B-xx（入口/复现/期望/实际/严重度/原始输出）
 ④ 台账**整批**交业务编写员修（不边修边测，避免轮次污染）
 ⑤ 修完由测试编写员为每个 B 条目补**回归用例**（先红后绿，必须能从用户入口复现）
 ⑥ 测试员会话**作废**（清空上下文，新 runId），回到 ①
退出：某一轮台账为空（P0/P1 = 0）且套件/e2e 全绿
```

### 11.56「一个反例」不足以下裁定：`<ul><p>` 不改树，不代表 `<li><li>` 也不改（R1 巡回，2026-11-19）

- 事实：我用 `append '<p>x</p>'` 到 `<ul>` 测了一次"解析后树不变"，就裁定了"内容模型只保 round-trip、`ul` 系列不拦"。
- 反例：审计员静态读 `content.ts:82-84` 后指出 `li>li`、`table>tr` 会**真的改树**；我复现：`append '<li>j</li>'` 到 `<li>` → `rc=0`，盘上 `<li hr-l1>i<li hr-…>j</li></li>`，重解析后 `j` 变成**兄弟**。用户说"追加进 li"，拿到的是兄弟。
- 教训：裁定"某类输入安全"时，**每个标签都要有证据**，不能用同类的一个实例归纳整类。派单里写"只拦 X 不拦 Y"这种边界，必须附"Y 类我逐标签验过"的记录，否则就是让写手替我的归纳背书。

### 11.57 可选结束标签不是结构错误：`<li>a<li>b` 是合法 HTML5（R1 巡回，2026-11-19）

- 事实：`replace` 用 `<ul><li>a<li>b</li></li></ul>` → `rc=1`「片段结构不完整：`<li>` 的结束标签没有对应的开始标签」。报文把**规范的容错规则**说成用户的错。
- 正解（F9 落地）：**先解析、后校验**——HTML5 容错解析把 `<li>a<li>b` 闭合成兄弟，再对**解析后的树**做根数与表格上下文校验；只有真丢内容才报结构错误，且报文必须给下一步。
- 教训：任何"校验用户输入"的代码，判据必须是**语义**（解析后的树），不是**字面**（标签配对）。

### 12.2 角色纪律（本模式下的强化版）

- **测试员不读 `src/`**：只读 `docs/`、`README`、`--help`、产物与真实输出。需要读源码才能判断的条目，标 `NEEDS_CODE_READ` 交协调者转审计员，**不许**自己去看。
- **台账只收"用户可见"的缺陷**：内部函数返回值不对但没有用户可见后果的，不记台账，记给审计员。
- **一轮只出一次台账**：禁止"测一条 → 修一条 → 再测"（会让"修好了没"无法归因）。
- **缺陷归属**：`B` 条目 → 业务编写员；`回归用例缺失/写不出` → 测试编写员；`用例假绿` → 测试员先证明再转测试编写员。
- **测试员换人不换标准**：新会话必须从 `<entrypoints 清单>` 与台账历史（读 `.workflow/reports/sweep-R*.md`，不读上一轮的对话）重新建立认知。
- **多人并行下仍只有一个 git 写者**：业务编写员独占 `git`；测试编写员与测试员不跑任何 `git` 写命令。

### 12.3 台账格式（`B` 条目）

```markdown
### B-07 <一句话标题>
- 入口: `hr serve demo.html` → 浏览器打开 /?doc=demo.html
- 复现: 1) … 2) … 3) …

- 严重度: P0（阻断）/ P1（功能受损）/ P2（体验）

```

### 12.4 为什么换"整批修"而不是"逐条修"

逐条修会把测试员变成立即验收者，等于让它参与修复过程（上下文被修复过程污染），于是下一轮它不再代表"第一次用这个产品的人"。**整批修 + 换人复测**，才保证每一轮都是"陌生人第一次上手"。

### 12.5 派单纪律：路径必须带 `file:line`，反问不算失败

- 派单里引用文件时**必须**写 `packages/<pkg>/src/<file>.ts:<line>`；只写路径等于给假前提（实例：我写过 `packages/core/src/errors/hr-error.ts`，实际是 `packages/core/src/hr-error.ts`，且"core 侧文案表"根本不存在）。
- 子代理发现派单前提不对，**应当先反问再动手**；反问不计为失败，凭假前提硬凑出来的实现才算失败（`docs/03` §11.20）。
- 同理，派单里禁止用"照抄 XX 的文案"这种**指代式**要求，要么给原文，要么允许对方按风格原创并在报告里注明。


### 12.6 测 `serve` 的三条铁律（四次踩坑后写死，2026-11-19）

**症状**：子会话的 `bash` 工具挂 240s 被系统报警，我 kill 掉 `hr serve …` 进程后 shell 才返回。R1 期间业务编写员踩了两次（`/tmp/r1f1-ev2.sh`）、R2 测试员踩了一次（`pid 72547`），合计浪费 ~20 分钟。根因是 `serve` **没有"跑完"这回事**，把它放前台就是无限等待。

**铁律一：永不前台跑常驻进程**。要么后台 `&`（拿到 `$!` 后**必杀**），要么 `timeout N`。
```bash
# A. 后台 + 轮询 + 收尾必杀
node --experimental-strip-types packages/cli/src/main.ts serve demo.html --port 8978 \
  --app-dir packages/app/dist --json > /tmp/s.json 2>&1 &
SPID=$!; sleep 2
URL=$(node -e 'console.log(JSON.parse(require("fs").readFileSync("/tmp/s.json","utf8")).data.url)')
curl -sS -D /tmp/h.txt "$URL" -o /tmp/b.html; echo "curl rc=$?"
kill $SPID

# B. 一次性、限时（超时 rc=124 是预期，不是失败）
timeout 15 node --experimental-strip-types packages/cli/src/main.ts serve … --port 8979
```

**铁律二：取 `rc` 时禁止接管道**。`cmd | tail` 得到的 `$?` 是 `tail` 的（`BUG-11` 曾被这样误判成 rc=0，前后骗了三次）。一律 `cmd > /tmp/o 2>&1; echo rc=$?`。

**铁律三：常驻进程留下的端口/pid 必须显式收尾**。收尾动作写进报告（`kill $SPID` 的退出码），否则下一轮"端口被占"会被误判成产品缺陷。

### 11.58 门禁收回协调者之后，派单模板必须带「prettier + lint 只查改动文件」（R2 F19，2026-11-19）

**症状**：F19 一轮里，`pnpm verify` **连续三次**死在第一关或第三关，每次都是一个 3 分钟的往返：`prettier --check` 红 `usage.ts`/`locate.ts` → 红 `r3-ambiguous-escape.test.ts`；`lint` 红 5 条 `max-lines-per-function`。写手每次都自证"我的用例全绿"，因为**格式与 lint 从来不在它们的自查范围里**。

**根因不是它们偷懒，是我的派单模板缺一行**。写手报告"验证：vitest 全绿"是真的，也是不够的。

**派单模板（每张单子结尾必须有两行，写死）：**
```bash
pnpm prettier --write <本次改动过的每个文件>   # 不是 --write .
npx eslint <本次改动过的每个文件>              # 不是 eslint .
```

**并附带一条**：写手**不许**跑 `pnpm verify`。全量门禁归协调者，理由有两条——① 一次 `verify` 3–6 分钟，塞进写手的盒子里就是超时的直接原因（R2 里三投三中超时）；② 写手自己跑全量，会诱发"为了让全量绿而改测试/改阈值"。

**顺带一条行数墙的读法**：`max-lines-per-function` 在**测试文件**上撞线，几乎总是"一个 `it` 在演一条完整旅程"。正确修法是按旅程分段拆 `describe`/`it`（R2 T13：4 条报错全落在 `describe` 回调上，拆成 8 个 `describe`，`it` 名与断言逐字保留，29→29）；**错误修法**是把断言塞进 `for`/`forEach` 压行数——行数绿了，坏了以后看不出是哪种输入坏的。

### 11.59 「一个盒子里只放一件事」（R2 F19，2026-11-19）

**症状**：F19 的写手连着两次超时（25 分钟 / 35 分钟），第三次救援只让它"写报告"，5 分钟收工。T13 第一次也是 25 分钟超时，而它的用例其实已经写完了——**只差报告**。

**读数**：超时不是模型慢，是**我把"改代码 + 验证 + 写报告"塞进了一个 25 分钟盒子**，而它的验证方式是跑测试套件（单次 1–3 分钟）。

**规则**：
1. **一个盒子只放一件事**：改代码 / 写报告 / 做变异 / 拆函数，四件事四个盒子。谁也不许"顺手把报告写了"。
2. **写测试的顺序是"全部写完，最后跑一次"**，不是"写一条跑一条"。
3. **超时前先落报告**：报告比代码重要，因为它是唯一的交接面。派单里写死这句。
4. 救援派单**必须先给"我已经验过什么"**（我跑的 6 文件 42 条全绿），否则被救的会话会从头再验一遍，第二次超时。

### 11.60 mock 会让死代码活着：覆盖率不是可达性（R2 F19，2026-11-19）

**症状**：`packages/core/src/ops/locate.ts` 有两处"防御臂"（`messageOf` 的 `String(error)` 分支、`bothFailed` 里的 `if (!(byId instanceof HrError)) throw byId`），覆盖率一直是 100%——因为 `packages/core/tests/locate-target.test.ts` 把 `parseSelector` 与 `resolveSelector` **两个都 mock 成"按顺序抛任意值"**，于是把"现实中不可能出现的输入"稳定地喂了进去。

**真相**：`attemptOrFailure` 只把 `isRetriable`（`invalid_selector`/`node_not_found` 的 `HrError`）收进 `failure`，其余当场 rethrow。所以那两条臂**在类型上就不可达**，它们防的是一个上游已经排除掉的输入。100% 覆盖率一直在为死代码背书。

**教训三条**：
1. **mock 的射程要写在文件头注里**：这个 mock 覆盖哪几条臂、剩下哪些臂由谁覆盖。`locate-target.test.ts` 的头注写了"为什么用 mock"，**没写"那命中路径谁测"**——答案是谁也没测，于是 `locateRealChain` 的成功路径账面 0 行（CLI 测试走 `spawn(MAIN)` 子进程，`@hreader/core` 解析到 dist，不记 src 覆盖率）。
2. **一个模块有 mock 版测试时，必须另有真链路测试**。R2 补上的 `packages/core/tests/locate-real-chain.test.ts`（13 条、零 mock）才是"这条命令能不能用"的证据；mock 版只配钉防御契约（"不可重试的内部错误原样上抛，不伪装成用户错"）。
3. **死代码的处置是删，不是忽略**。`v8 ignore`/`eslint-disable` 等于给死代码发身份证：它从此既不被测、也不会在重构时暴露。判死代码的标准不是"覆盖不到"，而是**"入口类型是不是已经把它排除了"**——是，就删。

### 11.61 一次全量 CI 才把 10 条红一次交出来：红会跨盒子累积（R2，2026-11-19）

**症状**：F18、F19、T13、T14 每个盒子都"自己的测试全绿"，最后我第一次跑 `pnpm verify`，test 阶段 **10 条红**——全部是 F18/F19 改了报文、改了码、增加了导出、收紧/放宽了 `#id` 字符集之后，**别处的旧断言**。

**根因**：我给写手的纪律是"不许跑 `pnpm verify`（全量归我）"，而写手就只跑"自己改的那个文件"。于是**改 src 的盒子**把红留给了别人，谁都没看见，攒了四轮。

**教训四条**：
1. **改 src 的盒子，必须跑"引用该模块的全部测试文件"**，不是只跑自己那个。`locate.ts` 被 CLI 四个测试文件间接覆盖，写手一个都没跑。
2. **全量红必须逐条分类**：`src bug` / `旧断言` / `flaky`。分类错了的代价是双向的——把回归当旧断言改掉（丢护栏），把旧断言当回归去改 src（改坏行为）。这次 10 条里 9 条是旧断言、1 条（`r2-locate-parity`）是**测试前提本身过强**。
3. **"逐字节一致"这类强前提要写清它约束的是什么**。那条测试要求"同一元素两条寻址路径输出逐字节相同"，而 `ambiguous_selector` 警告讲的是**选择器有歧义**，不是**元素是谁**——所以两份输出本来就该不同。弱化它的同时必须把护栏补回去（`span` 那条仍要带警告、子选择器那条不得带），否则放松会变成删掉护栏。
4. **协调者不能只在结卡前跑全量**。正确节奏：**每个盒子完成即跑一次 test 阶段（不跑 lint/build）**，贵一点但早知道；`verify` 全量留给我结卡前跑。
